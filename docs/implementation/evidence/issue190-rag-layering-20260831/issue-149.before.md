# 自然语言多工单客服 Agent 与知识工作台规格

## Problem Statement

当前项目已经完成真实 DeepSeek 接入、有预算的自主调查、受约束客户沟通、客服工单、人工接管、补偿提案、审批与执行等基础能力，但客户体验仍然接近“选择一个预定义物流问题后触发固定流程”。客户不能自然地描述一个订单上的一个或多个问题，不能在 Agent 回复后持续追加信息并进行真正的多轮沟通，也不能在同一客户身份下同时维护多张独立工单。Agent 的可见行为仍过度集中在确定性结论，难以展示其理解诉求、规划调查、组合证据、检索知识和自然解释的优势。

内部工作台同样没有形成完整的人类客服闭环。客服领取状态在页面切换、刷新或角色切换时可能表现得像临时 UI 状态，领取后缺少清晰的回复、标准补偿选择、提交审批和 Agent 辅助路径；同一订单的多张工单也没有统一分组。用户提供的高保真原型覆盖了大量有价值页面与状态，但正式 React 应用与原型在布局、信息层级、交互反馈和完整页面覆盖上仍有明显差距。

项目还缺少真实的客服知识能力。Agent 可以访问权威订单工具，却不能从版本化中文客服知识中检索规则说明并给出可追溯引用。若只把知识直接塞进提示词，会失去版本、适用范围、引用、评测和权限边界；若让 RAG 推断订单、支付或补偿事实，又会削弱 Spring 的业务权威。

需要在不扩大不可逆权限的前提下，把现有系统演进为受控的 L2 客服 Agent：以自然语言完成受理和问题归类；在客户确认后为同一订单的多个问题原子创建独立工单；允许各工单并行开展多轮流式对话与自主调查；以事实充分而非固定调查脚本支撑低风险结论；让客服在持久化领取后回复、选择标准补偿、提交审批并使用 Agent 辅助；引入受控的轻量中文 RAG；同时尽可能复刻高保真原型。所有资金、订单变化、授权、状态转换和副作用仍由 Spring 控制。

## Solution

在正式客服工单之前增加可恢复的受理对话。客户直接用自然语言描述诉求，无需预先选择订单或问题类型。Agent 依据当前客户可见的订单摘要提出订单候选，识别同一订单中的一个或多个问题，低置信度时用“你说的是不是……”一类自然澄清确认理解。客户通过自然语言或快捷按钮一次确认拟建工单集后，Spring 原子创建每个新问题对应的独立客服工单，并生成一份由这些工单共同引用的不可变共同受理记录。疑似重复问题必须经客户确认后继续既有工单，不能自动合并。一次受理对话只处理一个订单；若描述涉及多个订单，完成当前订单后保留描述并继续下一次受理。

客户和内部工作人员都按订单工单组查看工单，但分组只用于导航和协调。每张工单保持独立公开沟通、生命周期状态、处理模式、Agent 处理代次、负责客服、补偿和审批边界。统一创建的多张工单立即并行处理；同订单 Agent 只读取最小结构化同订单工单摘要，不能共享完整对话或自由形式记忆。客户可以在任一工单中持续追加信息；新消息使基于旧上下文的未完成生成失去公开响应权，并从最新对话重新处理。

Agent 采用受控 L2 自治。它自主决定调查路径、授权只读工具调用、知识检索和证据组合，并提出结构化证据集合及证据与结论的适用关系。Spring 不预先编排完整调查流程，只校验证据权限、来源、时效、已知冲突以及风险场景不可缺失事实。Agent 可以基于通过校验的事实充分证据形成低风险结论、请求澄清、推进等待状态、创建标准补偿提案或转人工，但不能修改地址、取消订单、批准或执行补偿、退款或发放权益，也不能覆盖 Spring 的资格和金额计算。

客户对话使用 Ant Design X 的对话组件表达等待首字、真实流式输出、来源和受控处理进度。浏览器始终只访问 Spring 授权 API 与 SSE，不连接 DeepSeek、Agent Server、Embedding 模型或知识存储。Agent 可以自然组织回复，但业务事实必须来自授权调查事实，规则说明必须关联知识引用，金额、资格和时效承诺只能来自 Spring 权威结构化结果。模型、工具或知识检索失败经过有限重试仍未恢复时，系统停止当前运行、保留进度并转人工，不切换假模型冒充完成。

只有 Spring 版本化白名单中的低风险场景，且完整回复已经持久化、事实充分、结论明确、无待办动作、无待审批补偿时，才形成自动解决候选。Spring 持久化五分钟期限并在到期时根据最新工单版本重新校验；期间任何客户新回复或“仍需帮助”操作都会取消资格。页面刷新、重新登录、SSE 中断或服务重启不会重置计时。进入已解决后仍沿用七十二小时关闭等待期与重开语义。

内部工作台持久化负责客服责任，页面切换、刷新、重新登录和实时连接中断不会令已领取工单消失。`HUMAN` 处理模式下只有负责客服可以公开回复；Agent 仅提供工单总结、知识检索、政策查询和回复草稿等无副作用辅助。客服从 Spring 允许的标准补偿方案中选择类型和理由并提交审批，不能任意覆盖金额；超出标准方案的诉求进入独立例外补偿申请。补偿仍按订单汇总全部工单的已执行、已批准、待审批和有效预占事实计算额度，防止多工单重复补偿。

第一阶段知识库使用仓库内版本化中文 Markdown 知识条目。Python/LangGraph 服务使用固定 revision 的 `BAAI/bge-small-zh-v1.5` 在本地 CPU 生成 Embedding；DeepSeek 仍是唯一负责推理和回复的对话模型。混合知识检索以 PostgreSQL 全文检索、pgvector 语义检索和 RRF 融合为首选基线，先用项目中文语料评测词法、向量和混合检索，不预先承诺 PostgreSQL 内建中文分词质量。知识查看、检索、版本和引用是真实功能；编辑、审核和发布页面尽可能复刻原型，但第一阶段明确显示“开发中”，不得伪造成功。

正式 React 应用以高保真原型为 UI 验收基线。已有页面、布局、信息层级、状态与交互尽可能复刻；领域模型变化和授权边界优先于原型。暂未实现但对系统有帮助的入口可以完整展示并反馈“开发中”，但发送、领取、审批、知识发布、补偿和其他业务动作不得伪造成功。实施采用可运行的端到端纵向切片，依次交付自然语言受理与多工单、客户多轮流式对话、内部持久化工作台、补偿与审批、RAG 和其余原型页面。

## User Stories

1. 作为客户，我希望直接用自然语言描述问题，以便不需要理解系统的问题类型。
2. 作为客户，我希望 Agent 从我的自然语言中识别订单候选，以便不必先使用订单选择器。
3. 作为客户，我希望看到 Agent 提出的候选订单卡片，以便能够确认它理解的是哪笔订单。
4. 作为客户，我希望未确认订单只作为候选存在，以便系统不会因猜测读取或操作错误订单。
5. 作为客户，我希望 Agent 自动识别物流异常、支付与退款、订单操作与规则以及其他问题，以便不必手动归类。
6. 作为客户，我希望 Agent 在不确定时询问“你说的是不是某个问题”，以便我可以用自然语言纠正它。
7. 作为客户，我希望一句描述中的多个问题被分别识别，以便不必逐个重复描述。
8. 作为客户，我希望 Agent 清楚列出同一订单的拟建工单集，以便我知道确认后会创建什么。
9. 作为客户，我希望用一句“可以”或一个快捷按钮统一确认拟建工单集，以便不必逐项点击。
10. 作为客户，我希望统一确认后多张工单全部创建或全部不创建，以便不会产生不可理解的半完成结果。
11. 作为客户，我希望确认前不创建正式工单，以便未完成的理解不会进入正式处理流程。
12. 作为客户，我希望确认前不启动工单服务级别目标，以便受理澄清和正式处理时间不被混淆。
13. 作为客户，我希望未完成受理在刷新、退出和重新登录后仍能继续，以便不会丢失已经描述的内容。
14. 作为客户，我希望未完成受理保留七个自然日，以便可以稍后回来完成确认。
15. 作为客户，我希望恢复归档受理时重新确认可能变化的订单事实，以便旧候选不会被当成当前事实。
16. 作为客户，我希望自动受理失败时能够由客服协助完成确认，以便模型故障不会令我无法建立工单。
17. 作为客户，我希望受理协助请求不会被误认为正式工单，以便补偿和服务时限不会提前生效。
18. 作为客户，我希望描述涉及多个订单时系统保留后续问题，以便完成当前订单后无需重新输入下一笔订单的问题。
19. 作为客户，我希望疑似重复问题先向我确认，以便系统不会错误合并两个不同问题。
20. 作为客户，我希望确认重复问题后直接继续原工单，以便相同问题不会产生重复工单。
21. 作为客户，我希望创建后的问题类型可以在有审计记录的情况下修正，以便分类错误不会迫使我重新描述同一诉求。
22. 作为客户，我希望发现独立新问题时再次确认并创建新工单，以便一张工单始终只处理一个问题。
23. 作为客户，我希望在订单总览中看到同一订单的所有工单，以便掌握整体处理情况。
24. 作为客户，我希望每张工单有独立状态和对话，以便不同问题不会互相污染。
25. 作为客户，我希望一次创建的多张工单立即并行调查，以便不需要逐张打开后才开始处理。
26. 作为客户，我希望订单总览集中显示各工单的受控处理进度，以便知道每个问题正在做什么。
27. 作为客户，我希望订单总览集中显示所有待我补充的信息，并标明所属工单，以便不会回复错位置。
28. 作为客户，我希望只能在对应工单内回答问题，以便回复不会错误广播给其他 Agent。
29. 作为客户，我希望完成一个问题后可以继续反馈下一个问题，以便一个客户可以同时维护多个诉求。
30. 作为客户，我希望在每张工单中与 Agent 持续多轮对话，以便可以逐步补充信息和追问。
31. 作为客户，我希望 Agent 生成期间仍能发送新消息，以便不必等待一个可能基于错误理解的长回复。
32. 作为客户，我希望新消息使旧的未完成回复失效并从最新上下文重新处理，以便不会收到过时答复。
33. 作为客户，我希望 Agent 开始处理但尚未输出文字时看到 loading 状态，以便知道请求已被接受。
34. 作为客户，我希望首个字符到达后看到真实流式输出，以便获得及时、自然的交互体验。
35. 作为客户，我希望看到“理解问题、核对事实、查询规则、整理回复”等受控进度，以便理解系统状态。
36. 作为客户，我希望看不到模型思维链、提示词、原始工具响应和技术异常，以便内部敏感信息不被暴露。
37. 作为客户，我希望 Agent 的回复能够自然表达，而不是只能返回预定义模板，以便体验接近人类客服。
38. 作为客户，我希望回复中的订单事实来自权威调查结果，以便模型不会编造当前状态。
39. 作为客户，我希望规则说明附带友好的知识标题和更新时间，以便可以理解回答依据。
40. 作为客户，我希望金额、资格和时效承诺来自 Spring 权威结果，以便模型建议不会被误认为业务承诺。
41. 作为客户，我希望知识与当前订单事实冲突时以当前权威事实为准，以便一般规则不会覆盖个案状态。
42. 作为客户，我希望 Agent 在模型、工具或知识检索失败时如实说明并转人工，以便不会收到伪造结果。
43. 作为客户，我希望系统不能偷偷切换假模型继续回复，以便“真实 Agent”声明保持诚实。
44. 作为客户，我希望明确要求人工后 Agent 停止公开回复，以便我的人工偏好得到尊重。
45. 作为客户，我希望低风险且事实充分的问题可以在给出明确结论后自动解决，以便不必等待人工关闭。
46. 作为客户，我希望自动解决前看到五分钟提示和“仍需帮助”入口，以便有机会继续沟通。
47. 作为客户，我希望五分钟内任何新回复都会取消自动解决，以便未解决的疑问不会被关闭。
48. 作为客户，我希望刷新、重新登录、断线或服务重启不会重置自动解决计时，以便状态一致。
49. 作为客户，我希望五分钟到期时系统重新检查最新状态，以便旧资格不会覆盖新消息或待办动作。
50. 作为客户，我希望已解决后七十二小时内仍能回复并重开，以便可以对结论提出异议。
51. 作为客户，我希望补偿提案显示为“待审批”而不是“已获得”，以便不会误解当前结果。
52. 作为客户，我希望只看到安全的补偿建议类型和金额，以便既透明又不暴露内部审批材料。
53. 作为客服，我希望按订单分组查看多个工单，以便理解同一订单的整体支持情况。
54. 作为客服，我希望领取一张工单不会自动领取同订单其他工单，以便责任边界保持独立。
55. 作为客服，我希望领取责任在页面切换、刷新、重新登录和 SSE 中断后仍然存在，以便工单不会瞬间消失。
56. 作为客服，我希望只有当前负责客服能够在 `HUMAN` 模式下公开回复，以便不会发生多人竞争发送。
57. 作为客服，我希望领取后能够查看业务时间线、调查事实和受控 Agent 行为，以便继续处理。
58. 作为客服，我希望直接撰写并发送客户回复，以便人工接管形成完整闭环。
59. 作为客服，我希望从 Spring 允许的标准补偿方案中选择类型和理由，以便无需手工计算金额。
60. 作为客服，我希望标准补偿方案不能任意覆盖金额，以便不会绕过补偿政策。
61. 作为客服，我希望标准方案不足时创建独立例外补偿申请，以便高风险请求进入额外审查。
62. 作为客服，我希望在 `HUMAN` 模式下请求 Agent 总结工单，以便快速掌握上下文。
63. 作为客服，我希望请求 Agent 检索知识、查询政策并起草回复，以便提高处理效率。
64. 作为客服，我希望 Agent 辅助结果必须经我审阅后手动发送，以便辅助不会越过人工责任。
65. 作为客服，我希望查看知识条目的标题、版本、内部标识和引用片段，以便核验 Agent 建议。
66. 作为客服，我希望看到结构化调查步骤、工具类型、动作结果、证据引用和决策理由码，以便理解 Agent 做过什么。
67. 作为客服，我希望看不到逐字模型推理、系统提示词和原始工具载荷，以便可观察性不扩大敏感面。
68. 作为客服，我希望同订单其他工单只提供最小结构化摘要，以便协调处理而不混入完整对话。
69. 作为客服，我希望 Agent 或工具在受理阶段失败时能在独立受理队列中接手，以便帮助客户完成工单确认。
70. 作为审批人，我希望补偿提案仍需人工审批，以便 Agent 自治不会扩大到资金授权。
71. 作为审批人，我希望审批证据仍以提案版本为范围，以便多轮对话不会扩大审批视图。
72. 作为审批人，我希望同一订单全部工单的补偿事实共同约束当前额度，以便避免重复补偿。
73. 作为审批人，我希望禁止自审、审批租约和版本失效规则继续生效，以便双角色人员不能绕过责任分离。
74. 作为维护者，我希望 Agent 自主决定调查路径和证据组合，以便系统真正体现 Agent 优势而不是固定 DAG。
75. 作为维护者，我希望 Spring 只校验证据权限、来源、时效、冲突和风险场景不可缺失事实，以便不预先编排完整调查流程。
76. 作为维护者，我希望模型主观置信度不能单独构成事实充分，以便高置信度幻觉不会获得业务权威。
77. 作为维护者，我希望低风险场景由 Spring 版本化白名单定义，以便自动解决边界可审计。
78. 作为维护者，我希望签收未收到、疑似丢件、重复扣款、退款异常、订单变更、补偿和事实冲突不能自动解决，以便高风险问题留给人工或后续动作。
79. 作为维护者，我希望完整消息作为权威记录长期保存，以便工作摘要不能覆盖真实对话。
80. 作为维护者，我希望 Agent 使用近期消息、可重建工作摘要、调查事实和知识引用控制上下文规模，以便长对话可持续运行。
81. 作为维护者，我希望不同工单不共享自由形式模型记忆，以便错误和陈旧事实不会跨工单传播。
82. 作为维护者，我希望知识条目具有稳定标识、版本、更新时间和适用范围，以便检索与引用可审计。
83. 作为维护者，我希望知识分段具有稳定来源和位置，以便回复可以回到具体 Markdown 内容。
84. 作为维护者，我希望 Embedding 模型只负责向量化，以便不引入第二个对话模型。
85. 作为维护者，我希望 `bge-small-zh-v1.5` 使用固定 revision 和校验值取得，以便构建可复现。
86. 作为维护者，我希望模型权重不进入 Git 且运行阶段不依赖临时联网下载，以便供应链和离线运行可控。
87. 作为维护者，我希望先用 PyTorch 建立 Embedding 正确性基线，以便 ONNX 优化有可靠对照。
88. 作为维护者，我希望 ONNX 只有通过向量、排序和资源验收后才能成为默认，以便优化不会改变检索语义。
89. 作为维护者，我希望混合检索结合词法与语义候选，以便同时覆盖精确术语和自然表达。
90. 作为维护者，我希望权限、发布状态、版本和适用范围在排名前过滤，以便高相似度内容不能越权泄露。
91. 作为维护者，我希望中文全文检索质量由项目评测决定，以便不会把未经验证的 tokenizer 能力当成事实。
92. 作为维护者，我希望知识文件缺失、索引过期或检索失败时停止无依据知识结论，以便 RAG 不会静默失真。
93. 作为维护者，我希望普通 CI 使用确定性模型响应并保持真实 LangGraph，以便测试稳定且不依赖外部费用。
94. 作为维护者，我希望真实 DeepSeek 验收具有固定模型、调用次数和成本上限，以便真实模型证明可控。
95. 作为维护者，我希望浏览器永远不持有 DeepSeek 密钥、Embedding 权重、Agent 地址或数据库连接，以便前端保持非模型信任区。
96. 作为设计评审者，我希望正式页面尽可能复刻高保真原型，以便实现效果与设计预期一致。
97. 作为设计评审者，我希望领域模型和授权边界优先于原型，以便视觉复刻不会引入错误业务行为。
98. 作为设计评审者，我希望未实现但有价值的入口显示“开发中”，以便页面完整但不伪造成功。
99. 作为设计评审者，我希望正常业务页面使用真实合成后端数据，以便 UI 不只是静态 Demo。
100. 作为评审者，我希望通过真实 Chromium、生产 React、Spring、PostgreSQL 和真实 LangGraph 验收，以便局部单测不能冒充完整产品能力。

## Implementation Decisions

1. 本规格是已完成 DeepSeek 安全接入、自主调查和受约束客户沟通后的增量，不重新建设通用模型 adapter、基础调查工具目录、补偿审批或执行框架。
2. 实施按可运行的端到端纵向切片推进：自然语言受理与多工单、客户多轮流式对话、内部持久化工作台、补偿与审批增强、轻量 RAG、其余高保真页面。
3. 正式客服工单之前引入持久化受理对话；受理对话不是客服工单，不启动首次响应或解决时长目标。
4. 一次受理对话只处理一个订单；多订单描述保留未处理内容，并在当前订单确认后开启下一次受理。
5. 客户不需要手动选择问题类型，也不强制预先选择订单；Agent 从自然语言和当前客户可见订单摘要提出订单候选。
6. 未确认订单只允许暴露最小候选摘要，不允许读取完整详情、提出补偿或产生订单副作用。
7. 问题类型第一阶段包含物流异常、支付与退款、订单操作与规则和其他问题；类型是 Spring 记录与校验的受控值，不是自由文本标签。
8. 低置信度订单或问题识别必须通过自然语言澄清，不能以模型置信度直接创建工单。
9. Agent 把同一订单的多个独立问题整理为拟建工单集，并以客户可理解的方式一次展示。
10. 自然语言确认和快捷确认按钮具有相同业务语义；确认请求使用稳定身份以支持安全重试。
11. Spring 在一次事务性业务操作中创建拟建工单集、共同受理记录和每张工单的关联；任何失败不得留下部分工单。
12. 共同受理记录不可变，包含原始诉求、确认订单、识别问题和客户确认；新工单通过引用共享该记录，不复制可漂移文本。
13. 疑似重复问题只是候选匹配；客户确认后继续既有工单，客户否认后允许创建新工单，系统不能自动合并。
14. 同一诉求的分类可以审计化修正；独立新问题必须重新确认并创建新工单。
15. 未完成受理持久化七个自然日，页面刷新、重新登录或 SSE 中断后可恢复；期满归档而不自动创建工单。
16. 恢复归档受理必须重新校验订单权属、候选摘要和可能变化的事实。
17. 受理阶段的 Agent、工具失败或客户人工偏好形成受理协助请求；该请求使用独立队列和权限，不继承客服工单的调查、补偿或审批能力。
18. 客户与内部工作人员都使用订单工单组作为顶层视图，但分组不是父工单，不拥有共享状态或处理权限。
19. 每张客服工单保持独立公开沟通、生命周期、处理模式、Agent 处理代次、负责客服、SLO、补偿提案和审批责任链。
20. 统一创建成功后各工单立即启动独立 Agent 处理，不依赖用户打开页面。
21. 同订单 Agent 只读取最小同订单工单摘要，包括问题类型、状态、待办动作和补偿流程存在性；不读取其他工单完整对话或自由摘要。
22. 同订单工单可以并行运行，Spring 的订单事实、补偿额度和授权校验负责仲裁共享业务约束。
23. 完整公开消息是权威记录；对话工作摘要是可重建材料，不得创造事实、覆盖消息或充当审计源。
24. Agent 上下文使用近期消息、对话工作摘要、当前调查事实、知识引用和当前工单授权范围内的最小同订单摘要。
25. 客户可以在 Agent 生成期间继续发送消息；Spring 接受的新消息递增处理代次或等价权威版本，使旧生成失去公开发送和业务副作用权限。
26. 旧生成已经产生的部分流式内容不得在新消息接受后继续追加为权威回复；客户端通过最新快照和代次恢复一致状态。
27. 对话 UI 采用 Ant Design X 的会话、气泡、输入器和来源组件；是否采用完整 X SDK 取决于与现有身份、快照、断线恢复和代次隔离的适配验证。
28. Spring 提供授权的流式产品事件，表达等待首字、内容片段、完成、终止、错误和快照恢复；浏览器不连接 Agent Server 或模型。
29. 公开处理进度只使用受控业务阶段，不包含逐字推理、提示词、原始工具数据、内部标识或供应商错误。
30. Agent 可以自由组织自然语言，但有依据的自然回复必须把业务事实绑定到调查事实，把规则说明绑定到知识引用，把金额、资格和时效绑定到 Spring 权威字段。
31. 回复发送前执行结构化证据范围、禁止承诺、敏感信息和当前处理代次检查；一次受控修正后仍不安全则转人工。
32. DeepSeek 是唯一对话与推理模型；固定假模型只用于明确的确定性测试配置，正式运行失败不能回退假模型。
33. Agent 自主决定调查路径、授权工具调用顺序、知识检索和证据组合；Spring 不实现一棵完整调查决策树。
34. Agent 提交结构化证据集合及证据与结论的适用关系；Spring 校验证据权限、来源、时效、冲突和当前风险场景不可缺失事实。
35. 模型置信度、证据数量或固定工具顺序均不能单独构成事实充分。
36. Agent 可以基于通过校验的事实充分证据自主形成低风险结论、请求澄清、等待外部信息、创建标准补偿提案或转人工。
37. Agent 不得修改地址、取消订单、批准或执行补偿、执行退款、发放权益、任意选择金额或覆盖 Spring 状态转换。
38. 低风险场景由 Spring 版本化白名单表达，而不是由问题类型或模型风险评分推断。
39. 第一阶段低风险场景只包括无争议、无待办的权威状态解释、纯规则或使用方法说明和已完成无争议的非补偿性信息核对。
40. 签收未收到、疑似丢件、重复扣款、退款异常、地址修改、取消订单、任何补偿、事实冲突和等待外部信息不得进入 Agent 自动解决。
41. 自动解决候选只有在完整回复持久化、低风险、事实充分、结论明确、无待办动作和无待审批补偿全部成立时创建。
42. 自动解决期限由 Spring 持久化为五分钟；客户端倒计时仅展示，不拥有业务计时权威。
43. 任何客户新回复或“仍需帮助”操作取消当前自动解决候选；到期任务必须锁定最新工单版本并重新校验全部条件。
44. 已被 Spring 接受的新回复在截止竞态中优先阻止自动解决；刷新、重新登录、SSE 中断和服务重启不重置期限。
45. Agent 自动解决后沿用现有七十二小时关闭等待期和重开语义；负责客服可以按既有权限立即手动解决，不受五分钟限制。
46. `AGENT` 与 `HUMAN` 是独立于生命周期的处理模式；同一时刻只有当前模式责任方可以公开回复。
47. `HUMAN` 模式下 Agent 只提供工单总结、知识检索、政策查询和回复草稿，不能自动发送或产生业务副作用。
48. 负责客服分配由 Spring 持久化；页面切换、刷新、重新登录和 SSE 中断不会释放分配。
49. 一张工单同一时刻至多一名负责客服；订单分组和领取其中一张不授予其他工单详情或处理权。
50. 客服可以发送公开回复、选择 Spring 允许的标准补偿方案与理由、形成补偿提案并提交审批。
51. 普通补偿提案不能任意覆盖金额或方式；超出标准方案的诉求使用独立例外补偿申请，不复用普通审批捷径。
52. 客户可以看到安全的待审批补偿类型和金额；内部人员按授权看到完整提案、证据和审批状态。
53. 补偿提案仍属于单张工单，但权威总可补偿额度、有效预占和剩余额度按订单汇总全部工单事实并并发仲裁。
54. 禁止自审、审批租约、不可变提案版本、执行与对账语义保持不变，Agent 不获得审批或执行身份。
55. 知识源是仓库内版本化中文 Markdown，至少包含稳定标识、标题、版本、更新时间、适用范围和正文。
56. 知识索引产生稳定知识分段标识，并保留条目标识、版本、适用范围、源文件和片段位置。
57. RAG 只解释客服知识和一般规则；订单、物流、支付、补偿资格、金额和执行结果必须来自 Spring 权威接口。
58. DeepSeek 继续是唯一推理和回复模型；本地 Embedding 只做 feature extraction，不形成业务判断。
59. 第一阶段 Embedding 首选固定 revision 的 `BAAI/bge-small-zh-v1.5`，记录来源、MIT 许可、文件清单与校验值。
60. 模型权重不提交 Git；构建或准备阶段取得，运行时从本地路径离线加载，文件缺失或校验失败时 fail closed。
61. 首先以 CPU PyTorch/Safetensors 固定查询指令、pooling、归一化、截断和向量维度，建立正确性基线。
62. ONNX Runtime 是优化候选；只有导出、向量差异、Top-K 一致性、冷启动、吞吐、P50/P95 和峰值内存验收通过后才设为默认。
63. 混合知识检索首选 PostgreSQL 全文检索、pgvector 稠密向量检索和 RRF，不先引入独立搜索服务。
64. 权限、发布状态、版本和适用范围在候选排名前执行硬过滤；相似度不能扩大知识可见性。
65. PostgreSQL 内建全文检索只作为最小基线，不预先承诺连续中文分词质量；项目评测不达标后再评估 `pg_trgm`、写入前分词或 PGroonga。
66. 小规模第一阶段语料优先验证精确向量搜索，不能在缺少规模证据时提前固定 HNSW 或 IVFFlat。
67. 知识与当前权威业务事实冲突时业务事实优先，并记录知识冲突；RAG 不自动修改知识条目。
68. 客户知识引用显示友好标题和更新时间；授权客服可查看条目版本、内部标识和引用片段。
69. 知识查看、检索、版本和引用必须连接真实数据；编辑、审核和发布第一阶段只复刻界面并显示“开发中”。
70. 正式 React 应用以高保真原型作为视觉和交互验收基线，不另建脱离业务的静态 Demo 应用。
71. 正常页面使用权威合成后端数据；只有明确标注的状态画廊可以使用固定展示状态。
72. 原型与领域模型或授权边界冲突时以领域和安全决策为准；偏离原型需要可解释记录。
73. 未实现但有产品价值的入口可以展示和点击，但必须明确显示“开发中”，不得伪造保存、发送、领取、审批、补偿或知识发布成功。
74. 所有浏览器请求保持同源进入 Spring；模型密钥、Embedding 权重、Agent 私有地址、数据库连接和内部工具接口不进入前端构建或网络。
75. 实施完成前必须从仓库根目录运行规范化检查；任何局部测试、演示或真实模型 smoke 都不能替代完整门禁。

## Testing Decisions

1. 单一主验收接缝是 Spring 向浏览器暴露的产品 API 与 SSE，由真实 Chromium 通过生产构建 React 访问真实 Spring、迁移后的 PostgreSQL、真实 Agent Server/LangGraph 和模拟补偿执行器。
2. 同一主接缝使用两种运行配置：普通 CI 使用确定性模型响应，发布验收使用有固定模型、调用次数、尝试次数和成本上限的真实 DeepSeek；两者不形成不同产品契约。
3. 普通 CI 不访问 DeepSeek、不需要模型密钥，但不得把 LangGraph、Spring 权威校验、PostgreSQL事务或 SSE 恢复替换成前端 mock。
4. 真实 DeepSeek 验收只使用合成业务数据；余额不足、限流、供应商异常或预算耗尽时诚实失败，不切换假模型，也不把未运行写成通过。
5. 测试断言外部可观察行为、领域转换、持久化不变量、授权决定和产品事件，不断言私有方法、图节点数量、唯一工具顺序、组件树或逐字自然语言。
6. 自然语言受理验收覆盖一个问题、同订单多个问题、多个订单、订单歧义、低置信度问题、自然语言确认、按钮确认和取消确认。
7. 受理事务测试证明统一确认全部创建或全部回滚，共同受理记录不可变，重试不会重复创建。
8. 受理恢复测试覆盖刷新、重新登录、SSE 中断、七日边界、归档恢复和变化订单事实的重新确认。
9. 受理协助权限测试证明客服只能完成订单和拟建工单集确认，不能在确认前调查完整订单、形成补偿或执行工单动作。
10. 重复问题测试覆盖正确匹配、错误匹配、客户确认继续旧工单、客户否认并创建新工单，以及同一拟建工单集内新旧问题混合。
11. 多工单测试覆盖同一订单原子创建、订单分组展示、独立生命周期、独立处理模式、独立负责客服和并行 Agent 运行。
12. 同订单摘要测试证明 Agent 只能读取允许字段，不能读取其他工单完整对话、自由摘要、内部记录或扩大处理权限。
13. 多轮对话测试覆盖连续追加消息、澄清恢复、长对话摘要重建和完整历史分页，证明摘要不会覆盖原始消息。
14. 生成竞态测试覆盖首字前新消息、流式中途新消息、完成边界新消息、旧代次迟到片段、迟到工具动作和断线快照恢复。
15. 流式 UI 测试覆盖 loading、首片段、持续更新、成功、错误、终止和重新连接，不用一次性假文本冒充流式输出。
16. 公开处理进度测试只允许受控阶段，拒绝 prompt、reasoning、checkpoint、线程或运行标识、原始工具载荷和供应商错误。
17. 有依据的自然回复测试覆盖订单事实、规则引用、金额与时效字段、知识冲突、无依据断言、越权承诺、敏感内容和一次修正后转人工。
18. 事实充分测试允许不同合法调查路径，只断言 Agent 提交的证据集合、适用关系、Spring 校验结果、风险不可缺失事实和最终业务不变量。
19. 事实充分负面测试覆盖越权证据、来源未知、过期事实、已知冲突、缺少风险必需事实和只有模型置信度的结论。
20. 低风险白名单测试覆盖每个允许场景和每个明确禁止场景，证明问题类型本身不能自动授予解决资格。
21. 自动解决测试使用可控时钟，覆盖完整回复持久化、五分钟前回复、恰好五分钟竞态、到期重新校验、待办新增、补偿新增、刷新、重新登录、SSE 中断和服务重启。
22. 已解决与重开回归继续覆盖七十二小时关闭边界、回复与关闭竞态、重开不重置既有 SLO 事实和已关闭后创建关联新工单。
23. 负责客服持久化测试覆盖领取、重复领取竞争、刷新、路由切换、重新登录、SSE 中断、释放、交回 Agent、解决、关闭和权限撤销。
24. `HUMAN` 模式测试证明只有负责客服可以公开回复，Agent 辅助不能自动发送或产生任何业务副作用。
25. 客服工作台真实浏览器验收覆盖按订单分组、领取、详情、业务时间线、公开回复、标准补偿选择、提交审批和 Agent 辅助草稿。
26. 审批回归覆盖待审批客户投影、审批租约、禁止自审、提案版本失效、批准与驳回、执行和待对账，不因多轮对话扩大审批视图。
27. 订单级补偿并发测试覆盖同订单多工单同时提案、审批、预占和执行，证明权威总额与剩余额度不会被重复消费。
28. 知识条目解析测试覆盖必需元数据、稳定分段、版本更新、旧引用审计、适用范围和无效条目拒绝。
29. Embedding 正确性测试固定模型 revision、查询指令、pooling、归一化、截断和向量维度，证明相同输入可重建。
30. ONNX spike 与 PyTorch 基线比较向量余弦差异、Top-K 排序、冷启动、吞吐、P50/P95 和峰值 RSS；收益或一致性不成立时保持 PyTorch 默认。
31. 中文检索评测使用真实项目知识语料构建 query、相关条目、错误版本和无答案集合，度量 Recall@K、MRR 或 nDCG、无答案精度和错误版本命中率。
32. 混合检索消融分别评测词法、向量和 RRF；只有混合方案达到冻结门槛后才固定候选数和融合参数。
33. 检索授权测试先执行权限、发布状态、版本和适用范围过滤，再排序；不可见条目即使相似度最高也不能进入结果或引用。
34. RAG 故障测试覆盖模型文件缺失、校验失败、索引过期、Embedding 失败、pgvector 不可用、无匹配和知识冲突，证明系统不补写无来源答案。
35. pgvector 与可选中文扩展必须验证迁移、升级、备份恢复、Compose 隔离和从空数据库创建，不得以 Python 包安装代替数据库扩展验证。
36. UI 高保真验收使用真实 Chromium 在桌面和窄屏比较原型覆盖的路由、布局、信息层级、加载、空、错误、断线、开发中和业务状态。
37. UI 可访问性测试覆盖键盘导航、可见焦点、对话流式更新的可理解状态、确认对话框焦点恢复、窄屏无横向溢出和基础屏幕阅读器语义。
38. “开发中”测试证明未实现入口可发现、可点击且不会发出伪造成功事件或改变后端状态。
39. 浏览器网络、产物和产品日志扫描继续拒绝模型密钥、Embedding 路径或权重、Agent 私有地址、数据库 URI、prompt、reasoning、原始模型输出、原始工具载荷、checkpoint 和内部 trace 标识。
40. 完整规范化门禁必须覆盖后端、Agent、前端、真实 PostgreSQL/LangGraph smoke、真实 Chromium 验收和 Compose 隔离；全部通过前不得提交实现。

## Out of Scope

- 不在本规格中实现真实支付、真实退款、真实物流提供商或使用生产客户数据。
- 不让 Agent 修改地址、取消订单、执行订单操作、批准补偿、执行补偿、退款、发放权益或绕过 Spring 权威。
- 不实现自动审批 Agent、客户预授权资金委托或 Agent 自审。
- 不建立通用多供应商模型平台；DeepSeek 仍是唯一正式对话与推理模型。
- 不把本地 Embedding 模型变成第二个对话模型，也不让它形成业务结论。
- 不建立跨客户或跨工单的自由形式长期记忆、客户画像或隐式共享上下文。
- 不把 LangGraph checkpoint、对话工作摘要或 RAG 索引当成业务事实源或审计日志。
- 不让 RAG 决定订单、物流、支付、补偿资格、金额、审批或执行事实。
- 不在未经中文项目语料评测前承诺 PostgreSQL 内建全文检索质量、ONNX 性能收益或具体内存占用。
- 不在第一阶段实现知识条目的在线编辑、审核、发布、回滚和完整知识运营后台；相关界面只显示“开发中”。
- 不引入独立 Elasticsearch、OpenSearch 或专用向量数据库，除非后续评测证明 PostgreSQL 基线不满足需求并形成新决策。
- 不把高保真原型直接作为生产代码复制，也不为了视觉一致绕过领域模型、权限和真实后端状态。
- 不伪造发送、领取、审批、补偿、知识发布或任何业务成功。
- 不在本规格中创建实施子票、修改业务代码、提交 PR 或合并；拆票与实施使用后续工作流。
- 不以单次演示、静态页面、jsdom、独立模型请求或局部 smoke 代替完整验收。
