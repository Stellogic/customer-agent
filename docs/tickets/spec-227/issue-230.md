## What to build

让同一订单的物流延迟和疑似重复扣款经一次确认创建独立工单，各自按新场景契约处理，刷新和追加消息后状态仍正确；维护者可以从这条真实产品路径完整核对受理、并行调查、回复与故障的调用归属和消耗，形成事先冻结、可复核的核心演示证据。

这不是只增加测试的分层票：交付多问题路径上的调用/usage 计量补齐、必要集成修正、失败诊断和核心范围重复验证。已有受理、原子建单、分组、围栏等满足规格的能力直接复用；不重复实现，也不承接无边界的新产品缺陷。新发现的独立缺陷另归实施票，本票记录阻塞。

## Acceptance criteria

- [ ] 基于前置两条场景路径及 #226 修复，真实浏览器从自然受理开始，一次确认原子创建物流延迟与重复扣款两张独立工单，保留共同受理记录及订单分组，不预写工单或业务结果。
- [ ] 工单分别使用本场景事实，调查/回复/人工终点与证据不串票；刷新恢复分组与公开状态，客服接手保留相应事实和未决问题。不修改确认后建单、独立责任和人工公开回复边界。
- [ ] 客户在真实生成期间追加消息，Spring 接受新消息后旧代次的迟到公开片段及副作用被拒绝，新消息持久存在；通过实际事件和持久状态证明围栏，不能只检查代次数字变化或界面提示。
- [ ] 复用现有模型审计接缝补齐受理 usage 和后续并行调用归属；可核对真实发生的逻辑调用、供应商尝试、已知 token 及费用，不能继续将受理操作数冒充精确供应商调用数。可用元数据不丢失，供应商未返回 usage 时保持未知。
- [ ] 同一场景下供应商、格式、发布、证据拒绝的受控诊断能定位能力、调用与缺失类别；不串并发调用，不保存原始 prompt/响应/思维链/秘密，不为此建立通用审计或费用平台。
- [ ] 通过带并发、故障和 usage 缺失的确定性端到端回归核对计量及状态；预算/授权检查不能被计量完善或拆分运行绕过。程序估算、供应商结算、PENDING 预留保持独立，旧费用与失败不删除、不重置、不自动释放。
- [ ] 提供可选择既有核心场景的有界诊断入口，仍通过正式 React → Spring API/SSE → PostgreSQL/LangGraph 路径。不新造产品测试接口、不直连模型/Agent 私有接口冒充验收，不把独立适配器诊断当产品成功。
- [ ] 先完成前置离线回归和受控诊断能力，再根据实际调用规模拟定一次明确的核心验证计划：固定版本、模型/提示/schema、合成样本、运行次数、尝试/token/成本/时间上限、停止条件及预期业务副作用；执行前取得用户的明确费用授权。
- [ ] 冻结矩阵包括物流无补偿、物流待审批、重复扣款说明后交人工、同订单拆票及恢复、生成中追加消息隔离。保留不同样本、每次执行、失败与未运行的完整分母；知识完整质量评测仍暂缓且不删原责任。
- [ ] 不以单次成功宣称稳定，不无限重跑直到通过或连续成功。正常场景因技术故障转人工计失败，预期重复扣款业务转人工按依据判定；部分成功不当成整个矩阵通过。关键费用未知、预算或全局故障等仍触发停止。
- [ ] 获授权后按冻结计划执行真实核心验证，保存可复核结果。若尚无授权、计划未执行或核心行为未满足，本票明确停在待执行/未通过状态，不用普通门禁替代真实证明、不为关票追加次数。报告仅说明冻结范围内的重复验证表现，不外推生产稳定性。
- [ ] 完成自身产品集成改动的回归、Standards/Spec 审查与最终版本完整规范化门禁；正式真实证据对应受测版本。代码或相关配置变化后不沿用不适用旧证据。
- [ ] 最终交付分别列已定位修复、两类场景契约、核心真实验证、未完成完整知识评测和 #174 原发布验收。核心票通过不关闭 #174，不恢复 PR #214 的自动关票行为或暂停运行。
