## What to build

让客户的疑似重复扣款工单仅依赖相关支付业务事实，得到有依据的支付与退款状态说明，明确尚未查明的部分，并保留上下文交人工核查。整条链路不再要求物流延迟、物流证据或无关订单规则，不能用假延迟值满足旧契约。

复用物流切片已经建立的权威必需事实策略与证据构造接缝，同步整理 Agent 调查、判断、回复和 Spring 结论/回复校验，而不是只从工具清单删掉物流读取。本票以该业务路径独立可演示且门禁通过为交付单位。

## Acceptance criteria

- [ ] 使用前置物流切片交付的统一策略接缝，不复制第二套证据规则，不重复实施 #226 已有修复。
- [ ] 按 Spring 支付场景策略核对订单、支付、取消/退款、既有补偿、待办及政策的业务依据；不得因旧代码要求而机械套用物流补偿政策。政策依据不足时如实走已确认的未决人工核查终点，不虚构依据或扩大权限。
- [ ] 程序读取实际必需事实并构造规则明确的真实证据关系，模型保留针对疑点的补查、追问、补充证据和自然说明；必需证据缺失仍拒绝，语义判断不由机械映射代替。
- [ ] 从实际能力与事实记录证明：重复扣款在未读取物流和订单规则时仍完成预期路径；不得预造事实、填零延迟、伪造物流引用或跳过 Spring 校验。
- [ ] Agent 的事实归一化、校验、判断、澄清恢复、客户沟通与结论不再对本场景要求延迟字段或物流引用，也不发起仅为物流补偿设计的无用判断。
- [ ] Spring 的结论输入、解析、服务校验和公开回复事实校验同步按场景处理，仍复核当前订单、代次、证据范围/来源/时效/冲突及状态。不得删除物流场景仍需要的约束。
- [ ] 当前模型和确定性测试模型经过同一支付场景契约。若迁移临时兼容旧形状，列清必要消费者及删除条件，不引入长期双轨；本票自身可独立合入并保持完整门禁通过。
- [ ] 客户回复仅说明现有支付、退款状态和未决问题，不把疑似重复扣款标记或客户描述说成已证实的逐笔扣款事实，不声称已退款或已查明原因。
- [ ] 正确终点是有依据的公开回复后进入人工核查，负责客服能看到已有事实与未决问题。技术故障导致的转人工单独记录为失败，不能因最终都为 HUMAN 而混算通过。
- [ ] 同一真实浏览器产品路径覆盖自然受理、确认、支付调查、回复、人工状态及刷新恢复；缺少支付必需事实和无依据金额/退款声明的负面回归继续有效，物流切片无回归。
- [ ] 失败诊断区分必需事实缺失、证据关系缺项与其他业务拒绝，关联正确能力和调用；不保存原始敏感载荷、不将历史 INVALID_EVIDENCE_APPLICABILITY 追溯成已确认具体原因。
- [ ] 完成回归、Standards/Spec 审查和最终版本完整规范化门禁后独立交付。本票不靠新付费整轮重跑证明代码正确，真实效果由后续冻结验证单独记录。
