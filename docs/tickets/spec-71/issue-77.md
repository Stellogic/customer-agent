## What to build

让同时承担客服与审批职责的内部工作人员在同一 Session 中安全访问两个工作区，同时建立不可绕过的补偿提案版本参与者约束。共享身份提高使用便利，但不得允许人员审批自己以客服身份参与内容的版本。

## Acceptance criteria

- [ ] 双角色内部工作人员登录后进入不加载业务数据的 `/internal` 选择页，并能进入客服和审批两个工作区。
- [ ] 系统对每个补偿提案版本权威保存以客服身份创建、修改或提交过内容的内部工作人员集合。
- [ ] 派生版本继承此前版本的客服参与者集合并追加当前版本参与者，不能通过复制或派生洗掉禁止自审。
- [ ] 只有不继承旧内容而独立创建的新补偿提案才重新建立参与者集合。
- [ ] 当前审批人的参与版本不出现在其审批队列中；前端过滤不作为安全证明。
- [ ] 即使绕过队列直接调用，领取事务也拒绝参与者本人并且不创建审批租约。
- [ ] 最终批准或驳回事务再次校验参与者集合，竞争、重放或陈旧租约都不能绕过禁止自审。
- [ ] 仅查看或曾负责客服工单、但未创建、修改或提交该提案内容的人员，不自动失去审批资格。
- [ ] 数据库迁移保留既有补偿提案和审批事实，并为可确定的历史参与事实执行确定性回填；不得通过重置基线数据规避升级。
- [ ] 使用真实 PostgreSQL 验证参与者唯一性、派生继承、队列过滤、领取与决定事务，并覆盖双角色 React 流程。
