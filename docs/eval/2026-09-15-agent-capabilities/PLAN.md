# Agent 能力评测：执行前冻结方案

状态：离线预检通过；尚未运行，尚无通过率。关联修复票 #242。以 `scenarios.json` 的 12 例及真实执行前保存的 `plan.json` 为本轮输入、顺序与参数依据。

## 要回答的问题

Agent 能否理解客户自然语言、在信息不足时澄清并理解否定、保持多问题/多订单上下文、利用事实组织直接回答、按需要补充调查与知识检索，以及识别人工意愿？自动业务合同与人工回答质量分别报告。机械必需事实读取由程序完成，不能算作模型自主选工具成功。

链路为 Chromium → React → Spring 业务 API/SSE → PostgreSQL/LangGraph → 真实 DeepSeek Pro。所有订单编号只写在自然语言正文，编号输入框保持空。SQL 仅准备本轮合成订单，以及只读采集和断言。没有预写工单、回复、调查事实或提案。未启动补偿执行器，不做审批，不执行补偿。

## 模型与预算

四角色受理、行动选择、业务判断、客户回复均使用 `deepseek-v4-pro`，不改提示、不换模型、不静默回退。实际请求/响应模型与提示/schema 版本逐请求记录。预计约 65 次调用；这是估计，不能保证全部跑满。

用户本轮最终授权：**10 元、80 次请求、160000 token、45 分钟**；先触达任一限额即停止后续请求。10 元取代本轮此前讨论的 1.5 元，不复用之前评测的任何账本。程序在每次调用前持久预留；未知 usage 保留 PENDING 并停止，不把预留当实际扣费。

主线程已于执行前核对 [DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)：Pro 未缓存输入按 9 微元/token、输出按 27 微元/token 保守估算。实际供应商扣费未知，不把估算或预留表述成真实账单。

为了观察已实现的补充调查能力，以下限额在**执行前**扩大，且仅通过本次 Compose 覆盖生效，不修改产品默认值：

| 调查动作循环限额 | 产品默认 | 本轮冻结 |
| --- | ---: | ---: |
| actions | 8 | 12 |
| provider attempts | 8 | 12 |
| tokens | 4000 | 16000 |
| cost micros | 100000 | 500000 |
| active wall-clock ms | 30000 | 60000 |
| repeated actions | 0 | 0 |

这些是 `ActionBudget` 调查动作循环限额；后续判断与回复模型不包含在其中，不能声称整个 Agent 代次只有 12 次调用或最多耗时 60 秒。整轮四角色仍共同受 80 次 / 160000 token / 10 元 / 45 分钟账本限制。模型内部已配置的有限重试会计费且逐次记录；案例 `retries=0`、单 worker、每例一次。普通失败继续收集，预算/未知计量停止后续用例，始终保存 PASS / FAIL / NOT_RUN。

## 数据与评分

1. `evaluation.spec.ts`：初次受理、澄清、各次确认、首代/追加终点的真实时间戳；受理原文、理解快照、所有客户/Agent/系统公开消息、事实、命令回执、审计/SSE、代次、提案、执行数、截图与失败。失败也执行尽力采集，采集错误单列。
2. `collect.py`：复用独立计量模块，另读取受控 checkpoint 的 `investigation_actions`、`modelCalls.selectedAction`、结构化结论及客户回复。模型实际选择的动作标记 `MODEL_SELECTED`，核心路径未经过模型选择的必需读取标记 `PROGRAM_REQUIRED`。缺失 checkpoint / 无法归属保留 UNKNOWN，不保存提示词、自由推理或原始供应商 payload。
3. 计量：逐角色/逐请求耗时、输入输出 token、结算状态、费用估算；按 intakeId/ticketId 关联案例。极少数未返回 intakeId 的调用如通过单 worker 时间窗归属，要显式记录关联方式。未归属和未知用量不能算零。
4. 时延：受理点击至响应、确认点击至建票/终点、追加点击至新终点、正文 UI 首次可见近似时点；报告 P50 与 nearest-rank P90、样本数。模型 `durationMs` 为完整请求/响应时间，不是 TTFT 或纯推理速度；固定业务时钟不能用于实时时延计算。
5. 自动业务合同通过率分母固定 12；旧路径单列。人工评分未完成时 `semanticReviewStatus=PENDING`、`capabilityAcceptance=null`，不把自动通过叫 Agent 能力全部通过。

对每条实际 Agent 公开正文单独人工打 0/1 分，并写原文依据：

| 维度 | 1 分 | 0 分 |
| --- | --- | --- |
| factConsistency | 与本票授权事实一致，清楚区分客户陈述与系统事实 | 与事实矛盾、串用其他订单、将疑似说成已证实 |
| directAnswer | 直接回答本轮明确问题，具体说明所问状态/所需信息 | 主要复述泛化模板，遗漏核心问题 |
| contextRetention | 保留已确认问题、否定/追加内容与本票上下文 | 忽略否认或新增内容、跨票混淆 |
| noFabricatedPromise | 正确说明审批/执行和未知信息，没有无据承诺 | 宣称未执行的退款/结案，编造确定送达/到账时刻 |

引用另记 `citationSemanticSupport` 为 0/1 或不适用：来源/版本/引文确实匹配只证明可追溯性，人工判断引用是否支持回答。第 11 例另逐项记录“规则回答”“指南回答”“承认准确时间未知”，不可由至少一项 optional 调用替代。没有正文的失败案例标 `NO_REPLY`，人工未评标 `PENDING`，不能省略案例或把未评算满分。无额外付费裁判模型。
