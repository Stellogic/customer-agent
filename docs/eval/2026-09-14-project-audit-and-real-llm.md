## 重要问题

后续已完成无付费离线诊断，确认普通失败终态的用量丢失分支，详见[支付失败原因分析及七组对照](2026-09-14-payment-failure-diagnosis.md)。原真实结果和账本保持不变。

### 1. 支付回复失败，且无法从现有记录定位具体流事件

本轮 `payment_handoff / sample 1` 完成订单确认、补偿及支付读取，动作选择 `SUBMIT_CONCLUSION`。客户回复请求 HTTP 200，耗时 7431 ms，但供应商调用记录为 `SCHEMA_MISMATCH`；业务记录为 `INVALID_MODEL_OUTPUT`，代次终点 `HANDED_OFF`。客户只得到固定转人工通知，没有预期的支付/退款事实说明。

因此已排除“没创建工单”和“动作模型提前选择 HANDOFF”作为**本轮**失败原因。HTTP 200 也不代表内容合同通过。没有失败原始流事件，不能断言是 JSON、事件序号、供应商终态还是其他具体字段导致。

代码定位：`agent/src/baseline_agent/deepseek_customer_communication_model.py` 第 147–177 行在流读取完成后才保存 payload，第 268–284 行将相关异常记为 SCHEMA_MISMATCH；流读取器的多处分支都抛出同类错误。本次 `validationDiagnostic=null`，不足以区分这些分支。

**最小后续动作**：针对这一条支付输入，先增加受控的流事件类型、失败检查点、是否收到终态及 usage 的诊断，禁止记录密钥；拿到脱敏失败片段后做离线回放，再决定修复哪一分支。无需先扩大业务架构或换模型，也不要靠放松业务断言制造通过。

### 2. 失败调用用量未知，使整批评测中止

同一客户回复调用的 input/output token 均为 null，账本保留 `PENDING`，预留 0.094320 元。前 20 次调用有用量，第 21 次没有。后五个样本由用例间预算检查标记 NOT_RUN。

未知用量停止调用是当前规则的正确执行，**不是建议取消的保护**。需要调查的是失败路径为何无法保留足够诊断与用量：供应商是否返回终态未知，不能把“本地没有记录”直接等同于“供应商没有返回”。不清除该笔预留，也不从本轮已知金额推算实际账单。

### 3. 现有计时与正确率口径容易产生误解

- `complete()` 固定等待 `COMPLETED`，最长 120 秒。支付样本已经转人工，测试仍等待到失败，所以 129.961 秒包含验收等待，不是模型生成耗时。后续可以在 `HANDED_OFF` 等不符合预期的终态出现时及时失败并附诊断。
- 正文现有断言主要是非空、可见；结构化事实通过不等于每句话正确。本轮补充人工语义核对，未新增付费裁判模型。
- 默认调查行动预算 30 秒，旧 batch03 使用 120 秒。本轮保持当前 30 秒默认值；该值只约束行动循环，不是包括受理、判断、回复在内的全链路 SLA。

以上属于局部可靠性和评测质量问题。本轮没有发现越权执行补偿或重复扣款的证据，但本次没有运行审批/执行路径，不能据此宣称这些路径已重新验收。
