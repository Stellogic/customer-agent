# 程序承担必需事实读取与规则明确的证据对应

真实验收反复暴露机械动作选择与证据声明失败，当前全局事实协议又使重复扣款依赖物流延迟。用户于2026-09-06确认：先稳定物流延迟、疑似重复扣款、同订单多问题核心路径，由程序执行业务规则明确的本场景最小必需读取，并从实际授权事实构造规则明确的必需证据关系；模型负责诉求理解、额外调查、追问、补充证据选择、知识语义判断和自然回复。正式规格为 [#227](https://github.com/Stellogic/customer-agent/issues/227)，对 [#149](https://github.com/Stellogic/customer-agent/issues/149) 作局部修订。

本决定部分替代 [ADR 0006](./0006-bounded-level-two-agent-autonomy.md) 中由模型决定全部必需工具顺序及全部证据组合的职责。保留原决定历史，以及其余受控自治、授权和业务权威边界。Spring 不编排所有可能的完整调查决策树，程序也不能代替模型判断知识是否足以回答。规则来源于 Spring 场景策略及业务依据，不保留彼此独立演化的多份必需规则清单。

首个实施切片 [#228](https://github.com/Stellogic/customer-agent/issues/228) 将物流延迟的最小必需范围限定为订单确认、物流、支付与退款、既有补偿与待办、适用政策。普通物流延迟判断不以订单规则为必需事实；规则查询仍可作为有明确目的的补充调查。重复扣款的消费契约调整由后续 #229 承接，本切片不宣称支付场景已经完成收敛。

机械证据映射只适用于实际取得的本工单、有效代次权威事实。缺失、过期、越权、冲突的事实仍拒绝，不补造证据、不把模型置信度当事实充分、不将支付记录或疑似标记推导为已证实重复扣款。来源、时效、事实冲突、资格、金额、状态转换、补偿审批和执行仍由 Spring 控制。

## 权衡与后果

- 放弃“必需步骤也逐次交模型决定、固定证据映射也全部由模型重述”的要求，以减少没有实质选择空间的模型调用与机械漏填；保留模型对额外调查和语义判断的自治。
- 不采用完整固定调查脚本或通用工作流平台。按场景调整事实、结论及回复契约，不能仅删除动作选择器中的必读项，也不能默认缺失延迟值来维持旧协议。
- 当前代码强制的读取不自动等于业务必需；物流延迟和重复扣款分别核对依据。重复扣款本阶段为有依据说明后交人工核查，不新增逐笔对账或自动退款。
- 确定性模型与真实模型使用相同产品契约。既有故障修复独立交付，随后定向重构与核心验证；#174 的完整发布要求及知识分层质量门不因阶段收缩而取消。
- 本文件记录已接受的决定，不表示代码已修改、完整门禁已通过、真实效果已验证或付费运行已获授权。
