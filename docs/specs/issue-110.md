# [规格] 将固定模型基线演进为 DeepSeek 驱动的自主客服 Agent

## Problem Statement

当前项目已经真实运行 React、Spring Boot、LangGraph、PostgreSQL、客服工单权限、客户澄清、人工接管、补偿提案、人工审批、补偿执行和 checkpoint，但 Agent 主调查流程仍固定调用 `fixed-fake-model-v1`。模型只在一个很窄的阈值判断位置重复确定性规则，客户描述没有进入模型，客户最终看到的结论也主要来自 Spring 固定文案。仓库虽然有独立真实模型 release smoke，但它只处理一条固定合成事实，不参与实际客服工单处理。

因此，当前产品能够证明业务流程、授权、并发和工作流持久化，却不能证明真实模型安全参与了工单调查，更不能提供客户可感知的自然语言理解与自主客服体验。如果直接把固定函数替换为一次外部调用，不仅无法形成真正的 Agent 能动性，还会保留模型伪造补偿方式和金额、失败后审计含义不清、供应商参数静默失效、调用成本不可控以及客户回复越权等问题。

需要把固定模型基线分阶段演进为使用 DeepSeek 的真实客服 Agent：先建立可评测、可影子运行、失败时安全转人工的真实调查判断模型；再让 Agent 在当前客服工单和处理代次范围内自主选择受控调查能力；最终让客户沟通模型理解合成客户描述和公开沟通，生成并自动发送经过 Spring 权威校验的客户回复。整个演进不能削弱 Spring 对授权、权威事实、补偿政策、金额、人工审批和补偿执行的控制，也不能让普通 CI 依赖外部模型。

## Solution

以三个正式里程碑递进交付，并把每个里程碑拆成独立、有序依赖的实施与验收票据。

第一阶段 B0 建立真实模型安全接入。先收缩 Agent 向 Spring 提交的调查结论，删除不具有权威意义的模型建议补偿方式和金额。建立领域化的调查判断模型接口，保留固定假模型作为普通 CI 和确定性测试实现，只新增 DeepSeek 实现，不建设通用多供应商平台。DeepSeek 使用其 OpenAI 兼容 Responses API 和严格结构化输出；先通过扩充后的合成评测集和业务路径影子运行验证 schema、业务不变量、失败率、延迟和成本，达到在对应实施票中预先冻结的门槛后，才允许真实模型向 Spring 提交结论。真实模型异常必须显式转人工，不得静默回退假模型。

第二阶段 B1 建立自主调查。把当前一次性返回全部调查事实的固定流程演进为有预算的迭代式工具调用。Agent 每轮从 Spring 授予的受控调查能力中选择一个结构化下一行动，例如确认订单、查询物流、查询支付和退款、查询既有补偿、读取适用政策、请求客户澄清、提交结论或转人工。Spring 在每次调用时继续验证机器身份、客服工单、当前处理代次、允许操作、幂等和业务状态，并只返回最小结构化事实与证据引用。Agent 可以自主决定调查顺序和何时结束，但不能访问数据库、任意内部端点、审批或执行补偿。

第三阶段 C 建立客户可感知的 AI 客服。调查判断模型与客户沟通模型保持两个不同接口，可以使用同一 DeepSeek provider，但具有不同输入、输出 schema、评测和失败边界。客户沟通模型读取当前客服工单授权范围内的合成客户描述、公开沟通和受控调查结果，形成包含客户可见文字、回复意图、证据引用和是否需要转人工的结构化回复。工单处于 `AGENT` 处理模式时，Spring 校验当前处理代次、生命周期、证据范围、禁止承诺和公开字段后自动发送；任何不确定、越权或失效结果都转人工。客户看到受控进度和公开回复，负责客服可以看到调查行动、事实和证据，审批人仍只能看到当前提案版本的审批证据，任何身份都不接触原始思维链或供应商 payload。

可见未来所有客户、订单、描述和消息均为合成业务数据。本规格仍按项目既有敏感数据边界管理这些数据，保持密钥隔离、最小发送和受控审计，但不把生产级真实客户数据合规作为当前完成条件。客服知识手册与 RAG 只有在准备好版本化合成语料和检索评测集后才作为后续增强；远期自动审批 Agent 需要新的参与者、委托权限、禁止自审和威胁模型，不属于本规格完成条件。

## User Stories

1. 作为客户，我希望 Agent 能理解我使用自然语言描述的合成客服问题，以便不必先理解内部问题类型和固定规则。
2. 作为客户，我希望 Agent 根据当前公开沟通保持同一问题上下文，以便后续回复不会忽略我已经提供的信息。
3. 作为客户，我希望 Agent 在缺少订单或必要事实时提出针对性的澄清问题，以便调查能够继续而不是直接失败。
4. 作为客户，我希望澄清问题只询问完成当前调查所必需的信息，以便不会被要求提供无关数据。
5. 作为客户，我希望工单由 Agent 处理时看到受控的调查进度，以便知道系统正在调查而不是页面卡死。
6. 作为客户，我希望 Agent 回复能够解释结论所依据的业务事实，以便理解为什么需要补偿、无需补偿或转人工。
7. 作为客户，我希望 Agent 回复不承诺未经批准的补偿金额、退款或完成时间，以便不会把模型建议误认为业务事实。
8. 作为客户，我希望模型输出失效、超时或不确定时工单可靠转人工，以便不会收到猜测性答复。
9. 作为客户，我希望已经明确要求人工后 Agent 停止自动回复，以便客户人工偏好得到持续尊重。
10. 作为客户，我希望旧处理代次的迟到模型结果不能发送消息或修改工单，以便不会看到过时调查覆盖当前处理。
11. 作为客户，我希望自动回复仍属于公开沟通并遵循现有重开与关闭规则，以便 AI 回复不会形成平行消息系统。
12. 作为客户，我希望 Agent 处理与客服人工处理有清晰状态，以便理解当前由谁主导调查。
13. 作为客服，我希望转人工后看到 Agent 已完成的调查行动、受控事实和证据引用，以便能够接续处理而不必从头调查。
14. 作为客服，我希望只看到当前分配允许访问的 Agent 调查记录，以便共享队列可见性不会扩大详情权限。
15. 作为客服，我希望模型失败被归类为稳定、可操作的转人工理由，以便区分需要补充事实、系统恢复或人工判断的场景。
16. 作为客服，我希望调查行动记录不包含模型思维链或原始供应商响应，以便可解释性不会扩大敏感数据面。
17. 作为客服，我希望 Agent 能自主选择订单、物流、支付、退款、补偿历史和政策等调查能力，以便处理过程不是固定阈值脚本。
18. 作为客服，我希望 Agent 在重复调用同一能力或调查预算耗尽时转人工，以便不会无限循环或消耗不可预测费用。
19. 作为客服，我希望 Agent 请求客户澄清、提交结论和转人工都保留幂等语义，以便网络重试不会产生重复业务动作。
20. 作为审批人，我希望补偿提案继续只包含 Spring 根据权威政策计算的方式和金额，以便模型不能影响最终补偿额度。
21. 作为审批人，我希望真实模型接入后仍需人工审批所有补偿，以便现有审批租约、禁止自审和责任链保持不变。
22. 作为审批人，我希望审批视图只显示当前提案版本的必要事实和证据，以便 Agent 调查能力不会扩大审批权限。
23. 作为审批人，我希望模型生成的自由文本不被当作审批依据，以便审批决定基于受控事实和政策。
24. 作为维护者，我希望调查判断模型拥有一个小而稳定的接口，以便 fake 与 DeepSeek 能通过同一测试接缝替换。
25. 作为维护者，我希望客户沟通模型与调查判断模型分离，以便两类能力可以独立评测、演进和失败转人工。
26. 作为维护者，我希望普通 CI 永远使用固定假模型，以便测试结果不依赖网络、额度、供应商波动或自然语言措辞。
27. 作为维护者，我希望真实 DeepSeek 评测只能显式选择并只发送合成最小事实，以便密钥和调用成本不会意外进入普通开发流程。
28. 作为维护者，我希望 DeepSeek 配置缺失或无效时显式失败，以便系统不会声称使用真实模型却静默回退 fake。
29. 作为维护者，我希望模型 provider、模型别名、后端指纹、提示版本和 schema 版本可追踪，以便供应商行为变化能够通过评测发现。
30. 作为维护者，我希望供应商不支持或静默忽略的参数由 adapter 白名单和契约测试拦截，以便 HTTP 200 不会被误认为配置正确。
31. 作为维护者，我希望模型输出在提交 Spring 前经过状态、JSON Schema、字段集合、枚举和证据白名单验证，以便结构化输出声明不成为唯一防线。
32. 作为维护者，我希望模型失败以受控结果返回，而不是把供应商 HTTP 和解析细节泄漏给 LangGraph 调用者，以便失败处理集中在模型模块内。
33. 作为维护者，我希望每次模型调用记录内部调用和尝试标识、供应商响应标识、模型、耗时、usage、缓存命中和失败分类，以便能够排查成本与可靠性问题。
34. 作为维护者，我希望调用记录不保存原始工单、完整提示、模型正文、思维链或凭据，以便可观测性保持最小化。
35. 作为维护者，我希望网络超时后的每一次供应商重试都被记录为独立尝试，以便重复调用和费用不会被伪装成一次请求。
36. 作为维护者，我希望模型调用具有明确的连接、读取、整体截止时间和最大尝试预算，以便供应商等待不会无限占用处理代次。
37. 作为维护者，我希望 400、401、402 和 schema 错误不自动重试，以便确定性配置错误不会重复产生调用。
38. 作为维护者，我希望 429、500 和 503 只有在整体预算内才有限重试，以便短暂故障可以恢复但不会形成重试风暴。
39. 作为维护者，我希望自主调查的每个工具都使用类型化输入和结果，以便模型不能构造任意 Spring 请求。
40. 作为维护者，我希望工具结果只包含模型完成当前任务需要的事实和证据引用，以便原始 HTTP、数据库字段和内部标识不会进入模型上下文。
41. 作为维护者，我希望自主调查允许不同合法工具路径，以便模型可以表现出真实的调查策略而不是复刻固定 DAG。
42. 作为维护者，我希望自主调查仍受最大行动数、墙钟时间、token、费用和重复动作预算限制，以便能动性具有确定性边界。
43. 作为维护者，我希望预算耗尽、模型拒绝、无有效输出和工具失败都显式转人工，以便任何失败都不会静默降级。
44. 作为维护者，我希望不同客服工单之间不共享自由形式模型记忆，以便错误、陈旧事实和身份信息不会跨工单传播。
45. 作为维护者，我希望 LangGraph checkpoint 只保存当前工作流恢复所需状态，以便 checkpoint 不被误用为客户长期记忆或知识库。
46. 作为维护者，我希望未来客服知识手册只提供带引用的非权威说明，以便 RAG 不会覆盖 Spring 补偿政策和业务事实。
47. 作为评审者，我希望能够明确区分 B0 真实模型接入、B1 自主调查和 C 客户沟通三个里程碑，以便交付声明不夸大当前能力。
48. 作为评审者，我希望 B0 在启用真实结论前具有可重复的 shadow 对比证据，以便上线资格建立在评测而不是演示印象上。
49. 作为评审者，我希望自主调查测试断言最终结果、安全不变量和预算，而不要求唯一工具顺序，以便测试允许合法的模型差异。
50. 作为评审者，我希望真实浏览器验收通过 React、Spring、真实 LangGraph 和 PostgreSQL 观察客户可见行为，以便 C 不能由独立模型 smoke 冒充。
51. 作为评审者，我希望客户、客服和审批人看到的 Agent 信息继续符合各自授权投影，以便新增 AI 能力不会破坏既有隐私边界。
52. 作为评审者，我希望 bundle 和网络检查继续证明模型密钥、Agent 私有地址、原始工具结果和供应商 payload 不进入浏览器，以便前端保持非模型信任区。
53. 作为演示者，我希望能够在合成场景中展示 Agent 自主选择调查步骤、请求澄清、形成结论和回复客户，以便项目真实体现 Agent 开发能力。
54. 作为演示者，我希望能够人为触发模型超时、拒绝、非法输出、预算耗尽和转人工，以便展示系统不仅在成功路径上工作。
55. 作为学习者，我希望 DeepSeek flash 与 pro 使用同一合成评测集比较正确率、延迟和成本，以便模型选择来自证据。
56. 作为学习者，我希望每个阶段独立 Issue、独立 PR 和独立正式验收，以便理解模型接入、自主编排和客户体验各自的工程难点。
57. 作为项目维护者，我希望 RAG 只有在存在版本化合成客服手册和检索评测集后才开始，以便知识库不是为了技术展示而提前引入。
58. 作为项目维护者，我希望自动审批 Agent 保留为远期探索并与调查 Agent 使用不同身份，以便当前规格不会预埋绕过人工审批的入口。

## Implementation Decisions

1. 本规格的完成目标是里程碑 C：在合成业务数据上完成自主调查与自动客户沟通。B0 与 B1 是必须正式验收的中间里程碑，不是最终产品声明。
2. 整体工作必须拆成有序依赖的独立实施与验收票据，不允许在一张票中同时完成模型接入、自主工具循环、客户沟通、RAG 和自动审批。
3. 第一张实现票只收缩 Agent 向 Spring 提交的调查结论：删除模型建议补偿方式和金额；保持当前 fake 流程、Spring 权威计算和用户可见结果不变。
4. 调查判断模型与客户沟通模型是两个独立模块和接口。两者可以共享 DeepSeek transport 实现，但调用者不需要了解供应商状态、HTTP、解析和重试细节。
5. 本规格只实现固定假模型和 DeepSeek 两个 adapter。fake 用于普通 CI 和确定性验收；DeepSeek 用于显式合成评测、shadow 和通过门槛后的正式运行。不建立通用多供应商插件平台。
6. DeepSeek adapter 优先使用官方 OpenAI 兼容 Responses API 和 `text.format` strict JSON Schema，不降级为只保证合法 JSON 的 Chat Completions JSON Output。
7. DeepSeek adapter 维护本项目允许的请求参数白名单，并对关键参数进行契约验证；供应商静默忽略未知参数不能被视为成功配置。
8. `deepseek-v4-flash` 是首个 shadow 候选，`deepseek-v4-pro` 只在同一合成评测集中做对照。最终模型由对应票据预先冻结的质量、延迟、失败率和成本门槛决定，不由价格或名称推断。
9. 模型配置必须显式区分 fake、shadow DeepSeek 和正式 DeepSeek。选择 DeepSeek 但缺少密钥或必要配置时启动或调用显式失败，不允许回退 fake。
10. 密钥只进入 Agent Server 的受限运行环境，不进入 Spring、React、仓库、镜像、默认 Compose 配置、日志或 checkpoint。
11. 可见未来所有客户、订单、消息和描述均为合成业务数据，但仍按现有合成业务数据敏感边界处理。生产级真实客户数据合规不是本规格完成条件。
12. 模型输入按能力最小化。B0 只发送受控结构化调查事实；C 只发送当前客服工单与处理代次授权范围内的合成客户描述、公开沟通和必要调查结果。
13. 不保存原始模型输入、完整输出、思维链、凭据或原始工具 payload。调查行动记录只保存动作类型、受控事实或证据引用和业务结果。
14. 模型调用可观测性记录内部调用与尝试标识、供应商响应标识、请求模型、响应模型、后端指纹、提示版本、schema 版本、耗时、usage、缓存命中和失败分类。
15. 每次供应商尝试拥有独立记录。没有供应商幂等保证时，网络结果不明确后的重试不能被视为同一次计费调用。
16. 调查判断模型只返回是否需要补偿复核及受控决策理由。订单、延迟和证据引用从已经验证的调查事实进入 Agent 结论，不由模型复述或发明。
17. Spring 继续重新读取当前权威事实，验证当前处理代次、订单、证据和状态，并独立计算补偿资格、方式和金额。
18. 所有补偿继续进入人工审批。Agent 不取得审批租约、审批决定或补偿执行能力，调查 Agent 不能审批自己的输出。
19. 模型失败对调用者表现为稳定、受控的业务失败类别；供应商 timeout、429、5xx、拒绝、空输出、非法 JSON、schema 不匹配和不支持参数等细节保留在内部调用记录。
20. 是否把具体供应商失败细分为不同转人工理由，由失败后的业务处理方式决定；没有不同处理流程时不把供应商细节扩散为领域枚举。
21. DeepSeek 先通过独立合成契约评测，再进入业务路径 shadow。shadow 调用不提交 Spring、不发送客户消息、不改变工单状态，只保存最小比较结果。
22. 从 shadow 切换为正式提交前，必须在对应实施票中冻结并达到 schema 成功率、业务正确率、拒绝或空输出率、P50/P95 延迟、成本和安全不变量门槛。
23. 正式 DeepSeek 失败时显式转人工，不允许在同一工单中改用 fake 生成业务结论。
24. B1 使用有预算的迭代式工具调用。模型每轮返回一个结构化下一行动，Agent 只从 Spring 授予的工具目录中选择并执行，然后把规范化结果返回下一轮。
25. 初始调查能力覆盖订单确认、物流事实、支付与退款状态、既有补偿和待处理动作、适用政策、请求客户澄清、提交调查结论和转人工。具体 HTTP 形状在实施票中冻结，不让模型构造任意路径。
26. 调查能力按当前客服工单和当前处理代次授权。Spring 在每次调用时校验机器身份、允许操作、generation、生命周期、客户人工偏好、幂等和业务状态。
27. Spring 工具 adapter 只向模型返回最小类型化事实和证据引用，不暴露原始 HTTP、数据库、内部令牌、完整业务对象或自由形式工具 payload。
28. 自主调查允许不同合法工具顺序，但禁止重复无进展动作。每个处理代次具有最大工具调用、墙钟时间、模型 token、费用、重复动作和供应商尝试预算。
29. 预算耗尽、无法取得必要事实、工具反复失败、模型输出无效或无法形成受支持结论时必须转人工。
30. 不建立跨客服工单自由形式长期记忆。当前工单公开沟通、调查事实和 LangGraph 当前处理代次状态是第一版唯一会话上下文。
31. LangGraph checkpoint 用于当前工作流中断和恢复，不是客户记忆、客服知识手册或审计事实源。
32. C 中客户沟通模型输出结构化 envelope，至少表达客户可见文字、回复意图、证据引用和是否需要转人工；具体 schema 由对应实施票通过评测冻结。
33. Spring 在自动发送前重新验证当前处理代次、`AGENT` 处理模式、生命周期、客户人工偏好、证据范围和禁止业务承诺。验证失败或结果迟到时不发送并转人工或丢弃旧代次结果。
34. 客户回复可以使用自然语言，但不能宣布未批准补偿、最终金额、真实执行结果、未经证据支持的事实或无法保证的响应时间。
35. 客户只看到受控调查进度和公开沟通；负责客服只在当前分配范围内看到调查行动、受控事实和证据；审批人仍只在有效审批租约内看到当前提案版本的审批证据。
36. 任何身份都不查看模型思维链、完整提示、原始供应商响应或原始工具 payload。可解释性来自调查行动、受控事实、证据引用和决策理由码。
37. 客服知识手册与 RAG 不属于 B0、B1 或 C 的强制完成条件。只有存在版本化合成语料、引用规则和检索评测集后才另立实施票。
38. 未来 RAG 只为客服手册、FAQ、操作规范和政策解释提供带引用建议，不能决定补偿资格、金额、审批或执行，也不替代结构化调查事实。
39. 自动审批 Agent 不属于本规格。远期若启动，必须作为独立机器参与者，在预先委托的场景、金额、风险等级和政策版本内运行，并单独设计禁止自审、审计和人工接管。
40. 模型失败码、shadow 阈值、调查预算、flash/pro 选择、客户回复 schema 和 RAG 指标由最接近实现的子票通过证据冻结，父规格不提前硬编码易漂移参数。

## Testing Decisions

1. 最高测试接缝是现有真实全栈行为：React 通过 Spring 与真实 LangGraph、迁移后的 PostgreSQL 和模拟补偿执行器交互。C 的客户可感知能力必须通过真实浏览器验收，不能由独立模型请求或静态 mock 冒充。
2. 普通规范化门禁始终使用固定假模型和确定性工具 adapter，不访问 DeepSeek、不需要模型密钥、不按自然语言逐字断言。
3. 调查判断模型模块通过同一个公共接口测试 fake 与 DeepSeek adapter 可观察结果。测试不穿透接口断言 HTTP client、内部解析函数或重试实现。
4. DeepSeek 真实模型评测是显式 opt-in release evaluation，只发送固定或应用生成的合成最小事实，并记录调用成本。缺少密钥时明确跳过，不能把未运行写成已通过。
5. DeepSeek Responses 契约测试覆盖 strict JSON Schema、required、enum、禁止额外字段、证据数组约束、输出上限、thinking 模式和不支持参数静默忽略。
6. 响应测试覆盖 completed、failed、incomplete、拒绝、内容过滤、空 output、多 output item、非法 JSON、schema 不匹配和截断。
7. 传输测试覆盖连接、读取和整体截止时间，覆盖 400、401、402、422、429、500、503 以及结果不明确的网络断开。
8. 重试测试证明确定性客户端错误不重试，暂时性错误只在整体预算内有限重试，每次尝试具有独立记录。
9. 模型调用记录测试断言必要元数据存在，同时证明密钥、原始输入输出、思维链、客户描述和工具 payload 不被持久化或打印。
10. Agent 向 Spring 的结论契约测试证明模型建议方式和金额已经移除，权威 facts 由受控 adapter 拼接，Spring 独立计算结论。
11. Spring 确定性复核测试继续覆盖延迟边界、订单状态、退款、既有补偿、待处理动作、政策版本、证据引用、剩余额度和并发提案。
12. shadow 测试证明真实模型输出不会提交结论、创建提案、解决工单、发送消息或改变处理代次，只产生最小比较记录。
13. shadow 评测覆盖 24、48、72 小时边界，以及取消、退款、重复补偿、错误证据、提示注入、拒绝、超时和无效输出。
14. 正式模型模式测试证明成功输出可以进入 Spring 确定性复核，任一模型失败显式转人工且不会回退 fake。
15. 自主调查使用工具目录接缝测试。模型只能选择允许的类型化行动，未知工具、错误参数、越权客服工单和旧处理代次都被拒绝。
16. 自主调查场景允许多种合法工具顺序，测试最终工单结果、证据完整性、业务不变量和预算，不断言唯一行动路径。
17. 自主调查测试覆盖缺少事实、订单歧义、事实冲突、工具暂时失败、重复无进展动作、预算耗尽和客户人工偏好。
18. LangGraph 恢复测试证明客户澄清后在当前处理代次继续，旧处理代次迟到行动不能产生副作用，checkpoint 不泄漏到产品投影。
19. 客户沟通模型测试覆盖意图理解、澄清问题、调查摘要、无需补偿回复、等待人工审批回复、转人工回复以及提示注入内容。
20. Spring 客户回复验证测试拒绝未经批准的补偿承诺、模型金额、伪造证据、越权订单、失效 generation、错误处理模式和不允许的公开字段。
21. 真实浏览器验收覆盖客户创建合成客服工单、Agent 自主调查、客户澄清、客户自动回复、转人工以及 SSE 断线恢复。
22. 客服浏览器验收覆盖当前分配后查看调查行动、事实和证据，分配撤销后立即清除受保护信息，并证明没有思维链或供应商 payload。
23. 审批浏览器验收继续证明领取前看不到证据、有效租约内才可决定、禁止自审、模型不能审批且自动客户回复不扩大审批视图。
24. 浏览器网络与 bundle 检查证明 DeepSeek 密钥、Agent 私有地址、模型请求、提示、原始响应、内部工具结果和 checkpoint 不进入前端。
25. 每个子票完成前从仓库根目录运行完整规范化门禁；只有真实模型显式评测可以因缺少调用者提供的密钥而条件跳过，其他门禁不得跳过。
26. B0、B1 和 C 各自拥有正式验收证据和诚实交付声明。局部 green、独立 smoke 或 jsdom 不能被描述为完整里程碑完成。

## Out of Scope

- 不在一张实施票或一个 PR 中完成本规格全部能力。
- 不在第一张实现票中调用 DeepSeek、修改客户体验、拆分调查工具或接入 RAG。
- 不建立通用多供应商模型平台，不同时交付 OpenAI、Anthropic、本地模型或任意 provider 插件体系。
- 不使用真实客户、真实订单、匿名化生产记录或真实支付数据；可见未来所有业务数据保持合成。
- 不把模型密钥放进浏览器、Spring、仓库、镜像、默认 Compose 配置或共享日志。
- 不让模型直接访问 PostgreSQL、任意 Spring 内部端点、补偿执行器或第三方退款系统。
- 不让模型决定权威补偿资格、方式、金额、审批、额度预占、执行或对账结果。
- 不允许调查 Agent 审批自己的补偿提案，不引入自动审批入口或隐式审批权限。
- 不保存或展示模型思维链、完整提示、原始供应商响应或原始工具 payload。
- 不建立跨客服工单客户长期记忆、客户画像或全局自由形式记忆。
- 不把 LangGraph checkpoint 当作知识库、审计日志或客户长期记忆。
- 不在没有版本化合成客服手册和检索评测集时接入 RAG、向量数据库或 Embedding。
- 不让未来 RAG 决定补偿政策、金额、审批或执行。
- 不以生产真实客户数据合规、企业 DPA、ZDR 或数据驻留作为当前合成项目的完成门槛。
- 不在本规格中创建子实施票、实现代码、分支、PR 或合并；拆票和实施需要后续独立授权与正式流程。

## Further Notes

- 当前主流程是 Spring 建立处理代次，Agent 获取结构化调查事实，固定假模型判断延迟阈值，Spring 重新读取权威事实并计算补偿；真实模型 release smoke 尚未参与该路径。
- DeepSeek 官方当前声明支持 OpenAI 兼容 Responses API 和 `text.format`，但兼容不代表语义完全一致，不支持参数可能被静默忽略。现有 strict JSON Schema smoke 是迁移起点，不是生产 adapter 已经验证的证据。
- DeepSeek 当前自动上下文缓存意味着响应对象显示不存储不能被解释为不存在任何服务端暂存；本规格因只使用合成业务数据而不阻塞，但仍要求最小输入和受控记录。
- 本规格遵循已接受的“受限工具循环实现自主调查”架构决定。工具是 Spring 授予 Agent 的能力，不是绕过业务权威的数据库访问。
- 本规格中的“更 Agent 化”指 Agent 能自主选择调查行动、识别信息缺口、请求澄清、形成证据链并回复客户，不指模型获得无限权限或不可逆业务主权。
- 客服知识手册适用于说明性、带引用的非结构化知识；结构化订单、物流、支付、补偿和政策执行事实继续来自 Spring 工具。
- 父规格发布后应按顺序拆分子票：调查结论契约收缩、模型 seam 与 DeepSeek 合成评测、shadow 接入、B0 正式切换、B1 工具目录与自主调查、C 客户沟通与真实浏览器验收。RAG 只有满足语料前提后再立票，自动审批保留在远期 Fog。
