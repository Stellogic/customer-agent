## Problem Statement

本规格是 #149 的局部修订，承接 #174 第14轮暂停后的用户确认，不重写已交付历史。项目当前的问题不是缺少更多功能，而是核心支持路径尚未形成可重复验证的结果：明确确认命令被模型重新解释，回复发布与纠正边界混淆，重复扣款结论多次因证据适用性声明被拒绝，整轮验收首场景失败又使后续场景长期无法验证。

第14轮仍为 INCOMPLETE，重复扣款结论再次被 Spring 以 INVALID_EVIDENCE_APPLICABILITY 拒绝。没有具体缺项或误绑定的历史证据，不能将候选设计追溯为已证实根因。普通组件检查、单次模型诊断和某轮部分场景通过均不能证明完整发布通过。

代码还把不同问题绑定到统一的全事实读取和物流延迟结论：Spring 场景证据策略未要求重复扣款读取物流，但后续结论及回复仍依赖延迟字段。模型逐次排列必读工具并重新填写已由规则规定的证据对应关系，增加调用和格式失败机会，却没有增加有意义的调查选择。

本项目是学习与展示项目。当前目标是先把有边界的核心场景做稳定、机制解释清楚，再继续完整知识问答质量与发布验收；不得通过删除旧要求或把故障转人工计为成功来实现收敛。

## Solution

交付物流延迟、疑似重复扣款、同一订单多个问题三条核心业务路径，并继续保证多轮追加消息、旧代次失效和刷新恢复正确。

对客户已确认的问题类型，程序依据 Spring 权威业务规则读取本场景明确必需的事实，并仅从实际取得的授权事实构造规则明确的必需证据对应关系。模型负责理解诉求、判断是否需要额外调查或追问、在授权能力内选择补充证据、判断知识是否足以回答并组织自然回复。Spring 继续校验来源、范围、时效、冲突、资格、金额、状态和副作用。

物流延迟依据物流和相关业务事实形成无补偿回复或待审批补偿提案；疑似重复扣款说明已知支付与退款状态、不能确认的部分，并保留上下文交人工核查。现有数据没有逐笔交易对账能力，不宣称已经查明两笔扣款原因或完成退款。同订单多个问题保持客户确认后原子建单、独立处理和分组恢复。

先将 #226 已定位缺陷整理为独立产品交付，再实施职责与场景契约调整，最后以离线回归、有界真实诊断、冻结核心端到端验证形成证据。完整知识问答质量评测暂缓，现有功能不因此删除，#174 也不因此降低或取消验收条件。

## User Stories

1. 作为客户，我希望用自然语言描述问题，以便不必理解系统工具和内部分类。
2. 作为客户，我希望订单与问题有歧义时得到必要澄清，以便系统不会依据猜测调查错误对象。
3. 作为客户，我希望点击明确确认按钮后按已确认内容建单，以便不被模型重新解释而停留在待确认状态。
4. 作为客户，我希望同订单多个问题一次确认后全部创建或全部不创建，以便避免半完成的受理结果。
5. 作为客户，我希望每张工单分别调查与沟通，以便不同问题不会互相污染。
6. 作为客户，我希望刷新后仍能恢复订单分组、工单和对话，以便无需重复描述。
7. 作为客户，我希望物流延迟调查读取当前权威事实，以便回复和补偿建议有真实依据。
8. 作为客户，我希望不符合补偿条件时得到明确解释，以便知道当前处理结果。
9. 作为客户，我希望符合条件的补偿显示为待审批，以便不会误认为已经批准或执行。
10. 作为客户，我希望疑似重复扣款根据支付和退款事实说明情况，以便不被无关物流状态误导。
11. 作为客户，我希望无法查明扣款原因时明确交人工核查，以便系统不会编造交易明细或退款承诺。
12. 作为客户，我希望模型能针对实际疑点补查或追问，以便调查不局限于固定完整脚本。
13. 作为客户，我希望追加消息使旧的未完成生成失效，以便不会收到基于过时上下文的回复。
14. 作为客户，我希望真实增量回复中的合法空白得到保留，以便显示内容完整自然。
15. 作为客户，我希望部分回复发布后失败不会从头重复发送，以便不收到重叠或矛盾内容。
16. 作为客户，我希望技术故障被诚实处理，以便不会将失败伪装为已解决。
17. 作为负责客服，我希望接手重复扣款时保留已核查事实和未决问题，以便继续核查而无需重新受理。
18. 作为负责客服，我希望人工处理模式下仍由我控制公开回复，以便 Agent 不越过人工责任。
19. 作为审批人，我希望资格、金额、审批和执行继续受 Spring 控制，以便此次调整不扩大 Agent 的资金权限。
20. 作为维护者，我希望程序执行规则明确的必需读取，以便模型调用用于真正需要判断的步骤。
21. 作为维护者，我希望不同问题只依赖本场景所需事实，以便重复扣款不因缺少物流字段失败。
22. 作为维护者，我希望必需证据关系来自实际授权事实和权威规则，以便不依赖模型机械复述映射。
23. 作为维护者，我希望缺失、过期、冲突或越权证据仍被拒绝，以便减少模型工作不会削弱业务校验。
24. 作为维护者，我希望模型仍能选择额外调查及补充证据，以便保留有意义的 Agent 自治。
25. 作为维护者，我希望每次失败能定位到具体契约类别和调用归属，以便不必反复付费才能逐层猜测。
26. 作为维护者，我希望确定性模型与真实模型经过相同场景契约，以便普通测试不继续掩盖真实路径缺陷。
27. 作为维护者，我希望已定位修复可以独立验证和交付，以便不被完整发布验收长期堵住。
28. 作为维护者，我希望验证前冻结样本、次数和费用上限，以便避免无限试跑和选择性报告。
29. 作为维护者，我希望预期业务转人工与故障转人工分别统计，以便通过率反映真实产品结果。
30. 作为维护者，我希望核心演示证据与完整发布证据分开，以便项目贡献及未完成范围可准确解释。

## Implementation Decisions

1. 保持 React 展示交互、Spring 业务权威、LangGraph Agent 的现有结构，不引入通用工作流平台或多供应商抽象。
2. 本规格在明确范围内替代 #149 关于“模型自行选择全部必需工具顺序和全部证据组合”的要求。程序承担规则明确的必需读取和机械证据映射，模型保留诉求理解、额外调查、追问、知识语义判断、补充证据选择及自然回复；Spring 不编排所有可能的完整调查决策树。
3. 新增架构决策，明确部分替代原受控 L2 自治决策的上述职责，其余权限边界继续生效。保留旧决策历史，同步领域术语与正式规格；领域词汇不承载工具清单或实现细节。
4. 必需事实以 Spring 的场景策略及其业务依据为权威。复用现有策略、能力和事实记录，不在提示和 Agent 中维护独立演化的必需事实清单。具体共享方式采用最小可行契约，不要求新规则引擎。
5. 区分“当前代码要求”与“业务必需”。物流延迟、重复扣款都不应因统一流程强制读取无关订单规则；重复扣款不应被物流字段约束。当前政策在支付场景的适用依据须核对；若依据不足，不伪造政策或自动套用物流补偿条件，按既定无法判明终点交人工。
6. 程序只能从本工单、当前有效代次实际读取的权威事实构造必需证据关系。不能为了通过而补造引用、默认缺失事实为正常、自动声明未验证的语义充分性，或把“存在支付记录”推导为“已证实重复扣款”。
7. 模型在已有授权能力和冻结预算内决定额外调查与追问。知识片段的语义充分性仍由负责回答的模型判断，不以必需事实映射替代知识判断；一般知识不能成为个案支付或补偿事实。
8. 调查模块按场景整理事实读取、归一化、验证、澄清恢复、判断、客户沟通及结论。后端同步整理结论解析、场景校验和回复事实约束，消除重复扣款对延迟字段的非业务依赖；不只调整动作选择器。
9. 确定性模型和 DeepSeek 复用相同的场景事实要求与业务校验。固定模型继续全读而真实模型裁剪的两套协议不视为完成。
10. 物流延迟继续保留补偿资格、既有补偿及待办、政策、支付相关校验。无补偿结果和待审批结果均需真实依据；自动解决资格、客户取消候选和既有期限不因本修订变化。
11. 重复扣款第一阶段以有依据说明并转人工核查为正确终点，不新增交易对账或自动退款能力。支付状态、退款状态与疑似标记不得被描述成完整交易调查结果。
12. 多问题受理、共同受理记录、工单独立性、刷新恢复、客户追加消息使旧代次失效、幂等和人工处理责任保持。
13. 保留真实增量回复。统一尚未发布、已开始发布、已结束的纠正资格；开始发布后不得通过从第0块纠正重发恢复。已有知识路径授权前缓冲和正文约束不改变。
14. 按实际调用归属记录审计，区分供应商请求、模型格式、内部发布和 Spring 业务拒绝。拒绝诊断可记录稳定分支码、缺少的事实或适用性类别及能力归属，不记录原始载荷或秘密；历史未知原因继续未知。
15. 核对并复用已有 usage 审计接缝，覆盖受理及并发调用的费用证据；未知 usage 不填零，程序估算、供应商结算和 PENDING 风险预留分别保留。本修订不重置历史费用，也不授权新付费调用。
16. 第一阶段先交付 #226 的已定位缺陷。逐项划分既有修复、提示候选和 #174 验收文档，不将混合 PR 整体当作已验证产品修复；提示候选不得写成已解决重复扣款拒绝。
17. 后续重构和核心验证作为本规格的独立纵向实施切片，不继续扩大 #226，也不把产品修复塞回纯验收 #174。每个切片满足自身回归、审查和完整规范化门禁后独立交付；局部测试、模型诊断或演示不能替代门禁。
18. #174 第14轮结束后保持暂停。PR #214 的产品修复、验收材料和自动关票关联须在后续拆分交付时核对，产品修复合入不得自动关闭尚未满足原要求的 #174；本规格发布不合并该 PR。

## Testing Decisions

1. 主验收接缝沿用已获用户确认的真实 Chromium → 生产构建 React → 同源 Spring API/SSE → PostgreSQL/LangGraph；不新增浏览器直连模型、Agent 私有接口或测试专用产品接口。
2. 同一产品接缝分别运行确定性模型配置和获授权的真实 DeepSeek 配置。普通门禁不付费，不用前端成功 mock、预写工单或内部发布调用冒充产品行为。
3. 优先复用现有自然受理、多问题原子建单、全栈客户追加消息与自动解决、流式发布、Agent action loop 及 Spring 证据充分性测试。低层回归只用于实际故障接缝，不替代端到端证据。
4. 断言外部业务结果、授权决定、持久化状态与事件。不匹配模型逐字文案、私有方法、图节点数或唯一工具排列。工具调用观察仅用于证明无需读取无关事实和核对消耗，不强制额外调查路径唯一。
5. 核心矩阵覆盖：物流延迟无补偿回复；物流延迟待审批提案且无越权执行；重复扣款有依据回复后交人工；同订单多问题原子建单及独立处理；刷新恢复；生成中追加消息的旧代次围栏。
6. 用真实能力记录证明物流不依赖订单规则、重复扣款不依赖物流或订单规则仍能完成预期结果；不能通过填假延迟值、预造事实或绕过 Spring 校验取得通过。
7. 缺少本场景必需事实、证据越权、过期、冲突时仍拒绝；模型高置信度、机械映射齐全或 HTTP 200 都不能代替事实有效和正确业务终态。
8. 回复回归覆盖合法空白片段、并发调用归属、发布错误分类以及已开始发布后禁止从头纠正；未发布路径保留既有有限纠正机会。不重复扩展与实际故障无关的极低概率用例。
9. 正常支持场景因网络、模型格式、内部发布等技术故障转人工计失败。重复扣款有依据回复后交人工才是该场景预期成功；同样的 HUMAN 终态必须区分原因，不能抹掉故障。
10. 开始新的付费验证前先保证失败诊断能标明契约类别，并完成相关离线回归。随后针对具体失败场景进行有界真实诊断，最后按冻结计划执行核心端到端验证；单次模型诊断不算发布证明。
11. 验证前冻结受测版本、模型及提示/schema版本、合成样本、次数、供应商尝试、token/费用与时间上限、停止条件和业务副作用，并取得执行授权。次数与金额由实际调用规模确定，本规格不虚设已验证的预算数字。
12. 所有执行结果与失败保留。不得无限重跑直到偶然或连续通过，不删失败分母，不在看过结果后降低门槛；关键费用未知、全局故障、预算或安全停止条件不得通过拆分场景绕过。
13. 每个实施切片运行相应回归、Standards/Spec 审查与仓库完整规范化门禁；最终测试与交付版本一致。报告明确区分离线回归、核心范围真实验证、完整 #174 发布验证和未验证范围。
14. 客户和客服完整知识回答质量评测本阶段暂缓，但原分层门槛、失败记录与责任归属保持。核心路径证明不能替代它们或使 #174 直接通过。

## Out of Scope

- 不整体重写 React、Spring、LangGraph，不新建通用 Agent/工具/工作流/供应商平台。
- 不扩大退款、补偿审批、执行、订单修改等不可逆权限。
- 不新增逐笔交易对账系统，不承诺查明重复扣款根因，不把疑似标记当确认事实。
- 不用固定完整脚本替代所有模型判断，不让程序宣称知识语义充分或任意补全结论。
- 不放宽证据有效性、公开回复事实约束、代次隔离或现有审批责任。
- 不删除已有知识问答功能，不取消原完整质量门和 #174 发布要求，不重新打开已关闭历史票来容纳新工作。
- 不把核心演示提升为生产可靠性承诺，不新增超出学习项目必要性的防御框架。
- 本次 to-spec 不创建实施子票、不修改产品代码、不运行付费模型、不提交或合并实现 PR；后续使用 to-tickets 拆分纵向切片。

## Further Notes

- 本规格来源于2026-09-06用户逐轮确认并最终接受的收敛方案，不是由失败次数自动推导的重写决定。
- 与 #149 的优先关系：本规格仅替代必需事实读取和规则明确证据映射的职责、补充两类场景契约及阶段交付顺序；#149 的其余产品要求、权限边界、知识分层质量门继续有效。原自动解决禁止场景不变。
- #226 调整为独立产品修复交付；既有提示候选及历史结果保留而不冒充已证实修复。结构性职责变化由本规格后续实施票承接。
- #174 保持纯发布验收与暂停，不复用旧 RunId、不新建外层重试。其恢复须明确授权且满足前置；核心阶段完成不等于原五场景或知识质量全部完成。
- 新实施票须在拆分时列清本规格故事、依赖、完成标准和原票关系。先复用 #226，再按可运行且可独立验证的纵向切片拆分，不按前端、后端、Agent机械分层拆票。
- ready-for-agent 表示规格可供后续拆票，不表示所有未知技术细节已有实现，也不是付费运行或恢复暂停任务的许可。
