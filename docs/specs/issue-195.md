# [规格] 为并行任务增加跨 worktree 测试门禁锁

## Problem Statement

当前多个独立实现任务可以并行开发和审查，但规范化测试、镜像构建、Docker/Compose、浏览器验收与最终本地完整门禁会竞争同一台开发机的 CPU、内存、端口、容器运行时和构建缓存。现行流程主要依赖协调线程口头禁止并发测试；一旦提示遗漏、任务恢复或线程绕过总入口，就可能同时启动重资源验证，导致资源挤占、结果不稳定、清理边界混乱和重复额度消耗。

仓库需要一个跨 worktree、跨 Cursor/Codex 进程的本机测试门禁锁，使并行开发保持高吞吐，同时从规范化脚本入口强制保证任一时刻只有一个任务运行测试或构建。锁还必须在进程崩溃后可靠恢复，并向协调线程提供可读、可判定的占用与残留状态。

## Solution

为当前 Windows 登录会话内的 customer-agent 仓库建立统一测试门禁锁：

- 使用 Windows 会话级命名互斥量作为唯一权威锁；
- 使用本机共享 JSON 状态记录展示当前占用者，但状态文件不决定锁是否有效；
- 所有仓库规范化测试、构建和门禁入口在执行重资源动作前必须获取同一把锁；
- 锁冲突立即返回结构化 TEST_GATE_BUSY，不等待、不轮询、不自动抢占；
- 重资源子脚本继承外层所有权令牌，拒绝无令牌的直接执行；
- 崩溃后由操作系统释放互斥量；若旧运行留下精确可识别的资源，则返回 TEST_GATE_RECOVERY_REQUIRED，由协调线程处理；
- 提供只读状态查询；
- 并行任务可以继续开发、双轴审查、频繁提交和保存 Draft PR，但未通过最终本地完整门禁前不得声明可交付、合并 PR 或关闭 Issue；
- 正式交付窗口继续按“同步最新 main、运行完整门禁、立即合并或取消”串行执行。

## User Stories

1. As an 实现 Agent, I want 在运行规范化测试前自动获取统一门禁锁, so that 我不会与其他任务争夺本机测试资源。
2. As an 实现 Agent, I want 在锁被占用时立即收到结构化状态, so that 我可以停止并报告，而不是长时间阻塞或反复轮询。
3. As a 协调线程, I want 看到当前占用锁的 Issue、RunId、进程和工作树, so that 我可以判断谁正在使用测试资源。
4. As a 协调线程, I want 通过只读命令查看 FREE、BUSY 或 RECOVERY_REQUIRED, so that 查询状态不会改变锁或运行资源。
5. As an 实现 Agent, I want 在不同 worktree 中竞争同一把锁, so that worktree 隔离不会造成虚假的并行安全。
6. As a Cursor 或 Codex 任务, I want 使用同一会话级互斥机制, so that 不同开发工具之间也不会并发运行重资源验证。
7. As an 实现 Agent, I want 纯代码开发和 Standards/Spec 双轴审查不占用测试锁, so that 三个任务仍可并行推进。
8. As an 实现 Agent, I want 在 PR 创建前频繁提交, so that 我可以保留可回滚的开发历史。
9. As an 实现 Agent, I want 在尚未测试时保存 Draft PR 并标记 CODE_READY_NO_TESTS, so that 远端可以保存成果但不会被误认为可合并。
10. As a 维护者, I want 测试门槛约束可交付状态而不是普通提交, so that 安全门槛不会破坏正常版本控制习惯。
11. As a 门禁入口, I want 将一次性所有权令牌传给重资源子脚本, so that 嵌套执行不会再次竞争同一把锁并形成自锁。
12. As a 重资源子脚本, I want 拒绝没有有效所有权令牌的直接调用, so that 任务不能意外绕过规范化入口。
13. As a 维护者, I want 持锁进程正常结束时必定释放互斥量并清除自己的状态记录, so that 后续任务可以继续验证。
14. As a 维护者, I want 持锁进程崩溃时由操作系统自动释放互斥量, so that 普通锁文件不会造成永久死锁。
15. As a 维护者, I want 陈旧 JSON 不被视为权威占用, so that 展示状态残留不会制造假死锁。
16. As a 协调线程, I want 在旧运行存在精确匹配的残留资源时收到恢复要求, so that 系统不会未经判断自动删除资源或继续运行。
17. As a 维护者, I want 锁释放时只删除与当前所有者令牌匹配的状态记录, so that 较早进程不会误删后来持有者的信息。
18. As a 维护者, I want 每次正式门禁记录所验证的 base SHA 与 head SHA, so that 合并前可以确认验证基线没有漂移。
19. As a 协调线程, I want 完整门禁到合并或取消的正式交付窗口保持串行, so that 一个已验证分支不会因另一个 PR 抢先合入而失去有效基线。
20. As a 维护者, I want 门禁后任何受版本控制内容变化都使旧门禁结果失效, so that 未验证修改不能沿用旧证据。
21. As a 维护者, I want GitHub Actions 保持关闭且本地完整门禁仍是唯一自动化测试门槛, so that 新锁不会悄然改变已确认的交付策略。
22. As an Agent, I want 在 AGENTS 工作约定中看到明确的状态机和禁止行为, so that 新线程无需依赖历史对话也能正确使用锁。

## Implementation Decisions

- 第一阶段仅保证同一台 Windows 机器、当前登录会话中的 Cursor 与 Codex 进程互斥；不引入跨机器协调服务。
- 使用固定、按仓库身份区分的 Windows 会话级命名互斥量。命名互斥量是唯一权威锁。
- 使用所有 worktree 可见、但不进入 Git 的本机共享 JSON 作为观察记录。记录至少包含状态版本、仓库身份、Issue、RunId、PID、命令类型、分支、worktree、HEAD、开始时间和随机所有者令牌。
- 状态记录写入和替换必须原子化；释放时仅允许当前所有者删除与自身令牌匹配的记录。
- 所有规范化测试、构建与门禁使用同一把排他锁。纯代码阅读、编辑、提交和 Standards/Spec 双轴审查不获取该锁。
- 锁竞争采用 fail-fast：立即输出机器可识别的 TEST_GATE_BUSY 以及人可读占用摘要，然后以稳定的非零结果结束。任务不得在内部排队、睡眠或循环重试。
- 提供只读状态查询，返回 FREE、BUSY 或 RECOVERY_REQUIRED。查询不得获取、释放或修改锁，也不得清理运行资源。
- 最外层规范化入口持有锁并创建所有权令牌；嵌套重资源子脚本只校验继承令牌，不再次获取互斥量。
- 未携带有效继承令牌的受保护子脚本返回 TEST_GATE_LOCK_REQUIRED，并且在启动 Docker、构建、测试服务或浏览器前退出。
- 仓库不尝试代理或拦截系统中的任意 docker、npm 或 Gradle 命令；工作约定禁止 Agent 绕过规范化入口。
- 正常、失败和异常路径都必须通过 finally 等价语义释放互斥量。进程崩溃后依赖操作系统的 abandoned mutex 语义恢复，不提供强制释放活跃互斥量的命令。
- 获取到已被异常放弃的锁后，先读取旧记录并进行只读残留检查。若不存在残留，可覆盖陈旧记录继续；若存在与旧记录精确匹配的容器、卷、网络或镜像，则返回 TEST_GATE_RECOVERY_REQUIRED，不自动删除。
- 只允许在权威互斥量确认为空闲时清理陈旧展示记录；不得用删除 JSON 的方式声称解锁。
- 正式任务应提供 Issue 编号；RunId 可以显式提供或由门禁生成。缺少 Issue 的人工运行标记为 manual，不能作为正式交付证据。
- 开发期间允许并鼓励频繁提交。代码与双轴审查收敛后可以推送独立分支并创建 Draft PR，以 CODE_READY_NO_TESTS 明示未完成验证。
- 完整门禁开始前必须同步最新 origin/main，并记录 base SHA 与 head SHA。通过后，在该 PR 合入或本次交付取消前，不得启动另一张票的完整门禁；聚焦测试仍可按锁的可用情况运行。
- 完整门禁后发生代码变化、冲突修复、基线变化或受版本控制内容变化时，原门禁证据作废。
- 工作约定必须说明允许的并行阶段、频繁提交、Draft PR 状态、锁错误处理、恢复升级路径、正式交付窗口以及本地完整门禁的唯一权威地位。
- 不修改客服业务领域词汇，也不创建 ADR；该能力属于可替换的工程运行机制，完整决策保存在本规格、工作约定和脚本帮助信息中。
- 锁任务为当前最高优先级基础设施任务。在它合入前，现有并行实现任务保持禁止测试；它合入后，各任务同步最新 main，再依次进入验证阶段。
- 锁任务自身执行测试前，协调线程必须确认其他实现任务均未运行测试。锁任务仍须完成实现技能流程、双轴审查、独占本地验证、最终完整门禁、PR 合入、Issue 关闭和 origin/main 回读。
- GitHub Actions 保持关闭；缺少 CI 检查不是阻塞。

## Testing Decisions

- 以规范化检查入口的跨进程外部行为作为最高测试缝；不以互斥量内部字段或私有函数调用作为主要验收依据。
- 使用至少两个独立 PowerShell 进程和两个独立 worktree 验证真实互斥行为。
- 锁协议测试使用独立的测试锁身份，不争用或污染正在运行的正式门禁锁。
- 验证空闲时第一个进程成功获取锁，并且只读状态能看到正确占用者。
- 验证第二个进程在任何 Docker、构建或测试动作前立即返回 TEST_GATE_BUSY。
- 验证正常成功、普通失败和异常抛出后，后续进程都能获取锁。
- 验证持锁进程被终止后，操作系统释放互斥量；陈旧 JSON 不会单独阻止新进程。
- 验证异常放弃且不存在残留资源时可以恢复；存在精确匹配残留时返回 TEST_GATE_RECOVERY_REQUIRED，并且不删除资源。
- 验证状态记录的原子更新和所有者令牌保护，较早持有者不能删除较晚持有者的记录。
- 验证所有受保护子脚本无令牌时返回 TEST_GATE_LOCK_REQUIRED，且不会启动 Docker/Compose、浏览器或构建。
- 验证总入口持锁时，嵌套子脚本继承令牌并能正常执行，不发生自锁。
- 验证工作树 A 持锁时，工作树 B 不能获取锁。
- 验证只读状态查询不会改变锁、状态记录或 Docker 资源。
- 验证完整门禁证据包含 Issue、RunId、base SHA 和 head SHA；基线或内容改变后旧证据不能继续使用。
- 锁任务交付前仍运行仓库最终本地完整门禁；该门禁由人工协调保证独占，因为新锁尚未合入。
- 测试不得依赖 GitHub Actions，不得启用或等待 CI。

## Out of Scope

- 跨机器、跨宿主或分布式锁服务。
- 为其他仓库提供通用锁服务。
- 操作系统级代理或拦截任意 docker、npm、Gradle、Java、Python 命令。
- 自动终止占锁进程。
- 自动删除异常运行留下的容器、卷、网络、镜像或业务数据。
- 为等待任务实现公平队列、优先级队列或后台轮询。
- 并行运行多个完整门禁。
- 重新启用 GitHub Actions。
- 修改客服业务领域模型、API、数据库或产品 UI。
- 在本规格阶段创建实现任务、运行测试或放行现有实现任务。

## Further Notes

- 当前 #163、#166、#191 可以继续开发、双轴 CR、频繁提交和保存 Draft PR，但在锁任务合入前不得运行测试、构建或门禁。
- 本规格只定义和发布工作，不授权立即实施。后续需由用户明确决定何时创建实现任务。
- TEST_GATE_BUSY、TEST_GATE_LOCK_REQUIRED 与 TEST_GATE_RECOVERY_REQUIRED 是稳定的机器可识别状态标识；实现可以补充中文说明，但不得依赖自由文本解析。
