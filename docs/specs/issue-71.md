# [规格] 统一客户帮助中心与内部工作台的登录、鉴权及路由

## Problem Statement

当前客户、客服和审批人虽然都由同一个 React 工程提供页面，但并未形成清晰、统一且可扩展的身份与界面架构。客户帮助中心、客服工作台和审批页面依赖手工路径分支进入；客服与审批人没有共享内部工作台外壳、登录态、导航和退出体验；浏览器请求仍可通过 `X-Synthetic-Customer-Id`、`X-Synthetic-Support-Id` 或 `X-Synthetic-Approver-Id` 表达人工身份。这种方式适合作为早期合成演示夹具，却不能证明“登录后由后端权威鉴权，并按权限进入不同界面”。

继续维护三套独立入口会重复建设登录态、设计系统、API 客户端、构建、测试和部署；反过来，让客户、客服和审批人共用同一个界面壳，又会把客户信息架构与内部工作台耦合，增加错误授权、敏感信息泄露和长期维护风险。同时，一个同时承担客服与审批职责的内部工作人员必须能访问两类工作区，但不能借角色切换绕过客服工单分配、审批租约、补偿提案版本或禁止自审规则。

需要建立一个可在本地完整演示、以后可接入组织 OIDC、同时保留现有业务权威边界的统一方案，并用真实浏览器、Spring、PostgreSQL 和 SSE 行为证明其成立。

## Solution

使用一个 React 应用承载三类参与者，但采用两个彼此独立的界面壳：客户通过 `/help/**` 使用 `CustomerShell`；客服和审批人通过 `/internal/**` 共用 `InternalShell`，并分别访问 `/internal/support/**` 与 `/internal/approvals/**`。客户和内部工作人员复用代码仓库、设计系统、API 客户端、构建与部署，不共用导航或数据投影。

Spring Security 使用同源 HttpOnly Session 作为浏览器人工身份边界。本地演示提供客户、仅客服、仅审批人和客服兼审批人四种固定账号，执行真实密码校验；客户与内部工作人员分别从 `/help/login` 和 `/internal/login` 登录。一个 Session 同一时刻只代表一个客户或一名内部工作人员，内部工作人员可以同时拥有 `SUPPORT` 与 `APPROVER` 角色。未来内部登录可以在维持相同当前身份契约的前提下替换为组织 OIDC。

前端通过 `GET /api/auth/session` 读取 `id`、`displayName`、`subjectType`、`roles` 和页面级 `capabilities`，再使用静态路由表生成菜单、路由守卫与默认落点。Spring 不下发 React 路由定义或路径；前端守卫只改善体验，所有 API、客服工单分配、审批租约、补偿提案版本和禁止自审规则继续由 Spring 权威执行。

保留现有 Vite 构建，渐进引入 React Router 7、Ant Design 6 与 Pro Components。各业务区域按路由延迟加载，以避免内部工作台依赖进入客户首屏；代码分包不作为安全边界。

## User Stories

1. 作为客户，我希望从客户专属登录入口登录，以便进入符合客户语境的帮助中心，而不是看到内部工作台。
2. 作为客户，我希望登录后默认进入 `/help`，以便直接查看和处理自己的客服工单。
3. 作为客户，我希望只能看到 `CustomerShell` 的导航和公开数据投影，以便不会接触调查事实、内部记录、补偿提案、审批租约或原始 Agent 数据。
4. 作为客户，我希望只能访问属于自己的客服工单，以便其他客户无法通过猜测标识读取我的信息。
5. 作为客户，我希望刷新页面后仍能从服务端 Session 恢复身份，以便不需要在每次刷新时重新登录。
6. 作为客户，我希望 Session 过期后被安全地送回客户登录入口，以便不会继续在陈旧身份下操作。
7. 作为客户，我希望退出后当前标签页及其他同源标签页都停止 SSE、清除缓存并回到客户登录入口，以便退出真正终止访问。
8. 作为客户，我希望内部工作台代码按路由延迟加载，以便内部依赖不会无故拖慢客户首屏。
9. 作为客服，我希望从内部工作人员登录入口登录，以便进入统一内部工作台。
10. 作为客服，我希望登录后默认进入 `/internal/support`，以便直接处理客服共享队列与已分配工单。
11. 作为客服，我希望只看到客服菜单和客服页面，以便不会因共享后台布局而误以为自己拥有审批权。
12. 作为客服，我希望直接输入审批 URL 时看到明确的 403 页面，以便系统不会通过静默跳转掩盖权限边界。
13. 作为客服，我希望客服工单详情继续要求当前有效分配，以便 `SUPPORT_WORKBENCH_ACCESS` 不会扩大为全量工单读取权。
14. 作为客服，我希望共享队列继续只展示最小摘要，以便统一工作台不会扩大未领取工单的数据可见性。
15. 作为客服，我希望可以创建、修改或提交补偿提案版本，同时系统记录我对该版本的参与事实，以便后续阻止自审。
16. 作为审批人，我希望登录后默认进入 `/internal/approvals`，以便直接处理有资格领取的补偿提案。
17. 作为审批人，我希望只看到审批菜单和审批页面，以便不会自动获得客服队列或完整客服工单权限。
18. 作为审批人，我希望审批队列只包含我有资格领取的提案版本，以便不会领取后才发现自己因自审规则无法处理。
19. 作为审批人，我希望审批视图仍受当前有效审批租约、租约令牌、租约版本和提案版本约束，以便页面 capability 不会替代资源级授权。
20. 作为审批人，我希望租约过期或提案版本冲突时收到 409，并刷新权威状态，以便不会把并发冲突误解为普通权限不足。
21. 作为审批人，我希望无权知道其存在的提案返回 404，以便提案标识不可被枚举。
22. 作为同时承担客服与审批职责的内部工作人员，我希望登录一次后在同一个 `InternalShell` 中看到客服和审批两个菜单，以便无需维护两个账号或两个后台。
23. 作为双角色内部工作人员，我希望默认进入轻量 `/internal` 选择页，以便自主选择本次要处理的工作区。
24. 作为双角色内部工作人员，我希望 `/internal` 选择页不预加载客服或审批业务数据，以便选择页不会意外扩大信息投影。
25. 作为双角色内部工作人员，我希望不能审批自己以客服身份创建、修改或提交过的提案版本，以便共享身份不会破坏职责分离。
26. 作为双角色内部工作人员，我希望派生提案版本继承旧版本的客服参与者集合，以便不能通过复制或派生新版本洗掉禁止自审限制。
27. 作为双角色内部工作人员，我希望仅查看过工单但未参与该提案内容时不会自动失去审批资格，以便自审限制保持精确而不过度扩大。
28. 作为未登录访问者，我希望访问受保护页面时进入对应的客户或内部登录入口，以便登录语境与目标界面一致。
29. 作为未登录访问者，我希望登录后只能返回经过校验的同源站内地址，以便恶意 `returnTo` 不能造成开放重定向。
30. 作为已登录但缺少页面 capability 的人员，我希望看到 403，而不是被自动赋予角色、静默切换身份或循环重定向。
31. 作为任意已登录人员，我希望前端只依据服务端返回的当前身份投影生成菜单，以便不会在浏览器中自行声明角色。
32. 作为任意已登录人员，我希望写请求携带有效 CSRF token，以便 Cookie Session 不会暴露于跨站请求伪造。
33. 作为任意已登录人员，我希望登录、退出或 Session 更新后重新取得 CSRF token，以便不会继续使用旧会话的 token。
34. 作为任意已登录人员，我希望一个浏览器 Session 同一时刻只代表一个主体，以便客户身份与内部工作人员身份不会叠加。
35. 作为任意已登录人员，我希望改用另一主体登录时替换旧 Session 并清除旧缓存与 SSE，以便上一主体的数据不会泄露给下一主体。
36. 作为任意已登录人员，我希望三十分钟无活动后 Session 过期，且首版不提供“记住我”，以便本地演示具有明确、可验证的会话边界。
37. 作为任意已登录人员，我希望人工身份 SSE 最长六十秒重新连接并重新鉴权，以便 Session 或资源授权失效后的陈旧访问窗口有明确上限。
38. 作为本地演示者，我希望登录页仅在 `local-demo` 环境显示四种演示账号辅助信息并可填充表单，以便快速验证各身份，同时仍经过真实密码校验。
39. 作为生产环境使用者，我希望登录页不显示演示账号辅助区域，以便演示夹具不会进入生产体验。
40. 作为维护者，我希望所有浏览器人工接口统一从 Spring Principal 获取身份，以便不存在部分接口仍信任 `X-Synthetic-*` 的混合安全模型。
41. 作为维护者，我希望机器身份继续使用独立、最小权限的认证链，以便 Agent 或补偿执行器不会借用浏览器 Session 或人工角色。
42. 作为维护者，我希望当前身份接口不返回默认路由或动态资源权限，以便 Spring 不与 React 页面结构耦合。
43. 作为维护者，我希望稳定的页面级 capability 仅包括 `CUSTOMER_HELP_ACCESS`、`SUPPORT_WORKBENCH_ACCESS` 和 `APPROVAL_WORKBENCH_ACCESS`，以便前端契约保持小而稳定。
44. 作为维护者，我希望登录成功、失败、退出和 Session 过期进入结构化安全日志，以便排查认证问题而不污染业务审计事件。
45. 作为安全审查者，我希望安全日志不记录密码、Session cookie 或 CSRF token，以便日志本身不会成为凭据泄露源。
46. 作为维护者，我希望首版使用单实例内存 Session，以便不为本地演示提前引入 Redis 或数据库 Session。
47. 作为维护者，我希望服务重启后要求重新登录，以便首版 Session 行为与其非持久化边界一致。
48. 作为维护者，我希望旧 `/support` 与 `/approver` 在首个统一工作台版本中仅做弃用重定向，以便现有演示入口不会立即失效且不会维护两套页面。
49. 作为维护者，我希望在下一次明确的路由清理版本中删除旧重定向，并在删除前核对链接、测试和演示入口，以便兼容逻辑不会无限期存在。
50. 作为未来集成者，我希望内部身份源能够在不改变当前身份接口与前端 capability 契约的情况下替换为组织 OIDC，以便身份提供商变化不会重写业务页面。

## Implementation Decisions

1. 前端保持一个 React 应用和一个发布单元，但划分为 `CustomerShell` 与 `InternalShell` 两个界面壳。客户与内部工作人员不共用导航和数据投影。
2. 正式路由为 `/help/**`、`/internal/support/**` 与 `/internal/approvals/**`。双角色人员的内部默认页为 `/internal`，该页只展示有权进入的工作区入口，不读取业务队列。
3. `/help/login` 与 `/internal/login` 是不同登录入口，可以复用表单和 API 基础设施，但不得提供登录后的产品级角色切换器。
4. Spring Security 是浏览器认证与粗粒度角色授权的权威边界。一个 Session 只绑定一个客户或一名内部工作人员；一名内部工作人员可以同时拥有 `SUPPORT` 和 `APPROVER`。
5. 本地演示提供固定客户、仅客服、仅审批人和双角色内部工作人员四种账号，执行真实密码校验。账号辅助区域只在 `local-demo` 中存在，选择账号只填充表单，不能绕过登录提交。
6. Session cookie 由 Spring 管理，保持 HttpOnly；生产环境启用 Secure，SameSite 策略应与同源部署和登录流程一致。首版 Session 在三十分钟无活动后过期，不支持“记住我”。
7. 首版使用单实例内存 Session，不引入 Redis、数据库 Session 或其他分布式会话组件。服务重启会使用户重新登录。
8. 写请求保留 CSRF 防护。SPA 获取独立 CSRF token，并以约定 header 回传；登录、退出及 Session 更新后必须重新获取 token。不得以“前后端同仓库”或“使用 JSON”为理由关闭 CSRF。
9. `GET /api/auth/session` 是恢复当前身份的唯一前端契约。已登录响应只包含 `id`、`displayName`、`subjectType`、`roles` 和 `capabilities`；未登录返回 401；响应不包含 React 路径、默认路由或动态资源权限。
10. 页面级 capability 固定为 `CUSTOMER_HELP_ACCESS`、`SUPPORT_WORKBENCH_ACCESS` 和 `APPROVAL_WORKBENCH_ACCESS`。角色描述人员职责；capability 只用于菜单、路由与页面体验。
11. 前端维护静态路由与 capability 映射：客户进入 `/help`，仅客服进入 `/internal/support`，仅审批人进入 `/internal/approvals`，双角色人员进入 `/internal`。后端不动态下发页面定义。
12. 前端路由守卫不是授权边界。每个 API 请求必须从服务端 Session 恢复 Principal，并重新执行角色、客服工单分配、审批租约、提案版本、客户归属和禁止自审等授权。
13. 所有浏览器人工接口必须在最终可运行版本中原子切换为 Spring Principal。产品运行路径不再读取或接受 `X-Synthetic-Customer-Id`、`X-Synthetic-Support-Id` 和 `X-Synthetic-Approver-Id`；测试改用受控 Spring Security 测试身份。
14. Agent 与补偿执行器等机器参与者保持独立的最小权限认证链，不使用浏览器 Session，也不被映射成人工角色。
15. 无认证 API 请求返回 401；已经认证但缺少页面或操作所需粗粒度权限返回 403；无权知道资源存在时返回 404；已经具有资源可见性但租约失效或版本冲突时返回 409。
16. `returnTo` 只允许映射到当前应用内经过认可的同源路径。不得接受协议、主机、协议相对地址或无法映射到已知静态路由的值。
17. 客服工单详情继续要求当前有效客服分配；客服共享队列继续只提供最小摘要。`SUPPORT_WORKBENCH_ACCESS` 不授予全量工单读取权。
18. 审批视图继续绑定当前补偿提案版本及有效审批租约。批准或驳回操作继续在事务内校验审批人、租约令牌、租约版本和提案版本。
19. 补偿提案版本必须保存以客服身份创建、修改或提交过该版本内容的内部工作人员集合。派生版本继承此前版本的参与者集合并追加当前版本参与者；只有不继承旧内容而独立创建的新补偿提案才重新建立集合。
20. 审批队列对当前审批人排除其参与过的提案版本；领取事务和最终决定事务都必须再次校验禁止自审，不能只依赖队列查询或前端过滤。
21. 禁止自审只针对参与提案内容的内部工作人员。仅查看工单或曾经负责工单但未创建、修改或提交该提案版本，不自动导致失去审批资格。
22. 人工身份 SSE 单次连接最长六十秒。客户端自动重连，每次重连重新验证 Session、角色和资源授权；六十秒是异常失联时授权陈旧的最大窗口。
23. 登录主体变化、退出或 Session 失效时，前端关闭 SSE，清除当前身份及所有主体相关业务缓存。退出使用同源跨标签页通知，使其他标签页立即执行相同清理；服务端 Session 失效仍是权威结果。
24. 前端保留 Vite，采用 React Router 7、Ant Design 6 与 Pro Components。不得整体迁移到 Ant Design Pro/Umi Max，也不以 react-admin 或 refine 替换定制的客服、SSE、审批租约与补偿状态流程。
25. `CustomerShell`、客服工作区和审批工作区使用 route-level lazy loading。必须通过生产构建与 bundle 实测确认依赖没有进入不需要的首屏 chunk；代码分包不作为数据隔离手段。
26. 旧 `/support` 和 `/approver` 在首个包含统一工作台的版本中重定向到正式路由并标记弃用，不保留旧页面实现。下一次明确的路由清理版本在仓库链接、测试和演示入口迁移完成后删除重定向。
27. 登录成功、登录失败、退出和 Session 过期写入结构化安全日志，不写入领域“审计事件”。安全日志不得包含密码、Session cookie、CSRF token 或完整敏感业务 payload。
28. 实施可以按测试驱动的小步推进，但最终交付不能处于一部分接口使用 Principal、另一部分接口使用合成身份头的混合状态。
29. 依赖版本只有在真实安装、类型检查、测试、生产构建和 bundle 分析通过后才能锁定。若 Pro Components 与选定的 React、Ant Design 或 TypeScript 版本不兼容，应优先保持既定架构边界，再以最小替代方案实现布局，而不是静默切换整套框架。
30. 未来组织 OIDC、分布式 Session 或客户/内部双构建入口必须保持当前身份、capability 和资源授权契约，除非另行形成并接受新的架构决策。

## Testing Decisions

1. 主测试接缝采用最高层的黑盒全栈行为：从真实浏览器登录开始，经 React、Spring Security、业务服务和真实 PostgreSQL，再从页面、HTTP 状态、数据库权威事实与 SSE 投影观察结果。测试不直接断言 React 组件内部状态或 Spring Security 内部类。
2. 全栈验收至少覆盖固定客户、仅客服、仅审批人和双角色内部工作人员四种账号，以及未登录状态。
3. 客户验收覆盖客户登录、默认进入 `/help`、只看到 `CustomerShell`、读取自己的公开投影、无法访问内部路由和其他客户工单、退出与 Session 过期后的清理。
4. 客服验收覆盖内部登录、默认进入 `/internal/support`、客服菜单、共享队列最小摘要、有效分配后读取详情、未分配详情 404、审批路由 403。
5. 审批人验收覆盖内部登录、默认进入 `/internal/approvals`、审批菜单、领取租约、提案范围视图、租约或版本冲突 409、客服路由 403。
6. 双角色验收覆盖进入轻量 `/internal`、同时显示两个授权入口、进入两类工作区、没有产品级身份切换器，并保持同一内部工作人员主体。
7. 禁止自审验收必须使用真实 PostgreSQL 覆盖：本人创建、修改或提交的版本不进入本人审批队列；直接领取仍被拒绝；决定事务再次拒绝；派生版本不能洗掉参与者；未参与提案内容的人仍可依法领取。
8. 认证负向矩阵覆盖每个人工 API：无 Session 为 401；错误粗粒度角色为 403；不可枚举资源为 404；有效可见性下的租约或版本冲突为 409。仅隐藏菜单不能算通过。
9. 明确验证所有 `X-Synthetic-*` 人工身份头在产品运行路径中不再被识别；携带伪造请求头不能改变当前 Principal 或资源可见性。
10. CSRF 验收覆盖无 token、错误 token、登录前 token、登录后新 token、退出后的旧 token，以及合法 token 的写请求。测试应证明关闭 CSRF 不是通过条件。
11. Session 验收覆盖登录时 Session fixation 防护、三十分钟无活动过期、不存在“记住我”、服务重启后重新登录，以及客户和内部工作人员之间登录时替换旧主体。
12. 跨标签页验收覆盖一个标签页退出后，其他标签页关闭 SSE、清空身份和业务缓存，并在下一次请求时得到权威未登录状态。
13. SSE 验收覆盖连接最长六十秒、自动重连、重连时重新鉴权、Session 失效、角色不匹配、客服分配撤销、审批租约失效和提案版本变化。不得把客户端定时器本身当作服务端授权证明。
14. React 行为测试覆盖静态路由映射、两种 Shell、四种身份落点、403 页面、受控 `returnTo`、旧路由重定向、路由延迟加载，以及登录主体变化后的缓存清理。
15. 生产构建验收应比较主要 chunk，证明客户首屏不会同步加载内部工作台业务模块。只记录实测结果，不预设未经测量的 bundle 数字。
16. Spring 层补充安全集成测试，用 MockMvc 或等价最高可用接缝覆盖当前身份接口、登录、退出、CSRF、角色矩阵和 HTTP 语义；避免只对控制器手工注入字符串身份。
17. 持久化与事务测试使用真实 PostgreSQL，验证提案版本参与者集合、派生继承、审批队列过滤、领取时二次校验和决定时最终校验，不能用内存数据库替代数据库确定性约束证据。
18. 保留并回归现有客户公开投影、客服工作台投影、审批视图、SSE 缺口恢复、审批租约、补偿执行和对账用例，证明统一认证改造没有扩大数据投影或破坏业务围栏。
19. 全栈验证使用隔离的 Compose project 和专用合成数据卷，不修改或删除基线资源；只有测试自身创建的资源可以在回读后清理。
20. 实现遵循 TDD：先建立能够因缺失行为而失败的测试，再实现最小行为并重构。完成前必须从仓库根目录运行 `pwsh ./scripts/check.ps1`，全部通过后才可提交实现。

## Out of Scope

- 当前不增加管理员、审计员、运营人员或其他内部角色。
- 当前不建设员工管理、角色配置、账号注册、找回密码、租户管理或通用系统配置后台。
- 当前不选择或接入具体组织 OIDC 提供商，只保留未来替换内部身份源的契约边界。
- 当前不引入 Redis、数据库 Session、集群会话复制或多实例部署方案。
- 当前不实现“记住我”、长期登录或客户与内部工作人员之间的免退出身份切换。
- 当前不允许客户匿名创建或查看客服工单；客户通过客户登录入口建立身份。
- 当前不把客户、客服和审批人拆成三个仓库或三个独立前端。
- 当前不让客户与内部工作人员共用同一个页面壳、菜单或数据投影。
- 当前不整体采用 Ant Design Pro/Umi Max，不采用 react-admin 作为主框架，也不因未来 CRUD 设想提前引入 refine。
- 当前不由 Spring 动态下发 React 路由树、组件名、菜单配置或页面定义。
- 当前不把前端菜单、路由守卫或代码分包视为安全边界。
- 当前不修改 Agent 与补偿执行器的既有业务能力，只保持其独立机器身份边界。
- 当前不重构与统一身份、界面壳、提案参与者或测试接缝无关的业务流程。
- 当前不承诺未经实测的 bundle 大小、生产吞吐、组织级高可用或真实生产身份安全等级。
- 旧路由的最终删除属于下一次明确的路由清理版本，不在首个统一工作台版本中执行。

## Further Notes

- 本规格基于已经接受的三个架构决策：一个 React 应用使用两个界面壳；渐进采用内部工作台组件栈；分离登录入口并保持单主体 Session。
- 开源项目和官方文档调研结论是：参考 Ant Design Pro 的信息架构，在现有 Vite 中使用 React Router、Ant Design 和 Pro Components；refine 仅在未来出现大量标准 CRUD 模块时再做隔离验证；react-admin 不作为当前主框架。
- 现有客服有效分配、审批租约、补偿提案版本、客户公开投影及 SSE 自愈契约都是必须保留的业务围栏，统一登录和共享布局不能替代或弱化它们。
- 当前依赖组合尚未完成真实安装、类型检查、生产构建与 bundle 实验，因此实现阶段必须先用测试和构建证据确认具体兼容版本。
- 本规格适合作为后续拆分纵向实施票据的父规格；后续票据应按认证基线、资源授权迁移、提案参与者约束、两个 Shell 与路由、全栈验收等依赖顺序拆分，不能并行交付彼此依赖的安全边界。
