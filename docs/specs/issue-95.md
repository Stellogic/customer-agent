## Problem Statement

当前客户帮助中心、客服工作台和补偿审批工作台已经具备真实登录、路由、数据投影、SSE 恢复、客服工单分配与审批租约等完整业务边界，但界面仍主要服务于功能验证：页面之间的视觉语言不统一，客户侧缺少温暖、清晰、解释性的服务体验，内部工作台也没有形成适合桌面高密度操作的稳定信息层级。加载、空数据、错误、断线、重新同步、权限撤销、租约失效和操作结果未知等关键状态虽然在行为上存在，却没有全部形成一致、明确的视觉反馈。

仓库中的高保真 HTML 原型已经给出了期望的整体设计方向，包括森林绿与深军绿配色、米白画布、衬线标题、克制的圆角和阴影、客户侧的解释性布局、内部工作台的高密度桌面布局，以及队列、预览、时间线、证据、确认弹窗和状态反馈的表达方式。但该原型使用模拟数据和静态交互，其中大量字段、页面、按钮、统计指标与业务承诺并不存在于当前真实 API。如果逐项照搬，会制造虚假数据、不可执行操作或错误权限暗示；如果只做局部换色，则无法获得原型已经形成的完整产品体验。

需要在不改变既有业务契约和安全边界的前提下，让正式 React 前端整体采用原型的视觉设计与信息组织方式，并只呈现仓库现有实现能够权威支持的数据、权限、状态和操作。

## Solution

以高保真 HTML 原型作为正式前端的视觉与体验基准，统一客户帮助中心、内部登录与工作区选择、客服工作台、审批工作台以及全局状态页面。正式实现复用原型的配色、字体层级、空间节奏、桌面布局、状态语义和交互反馈，但根据当前真实 DTO、路由和权限投影重新编排内容，不复制原型的模拟数据结构。

客户侧保持温暖、轻量、解释性强的体验，围绕创建客服工单、查看公开沟通、补充客户澄清、请求转人工、回复已解决或已关闭工单以及连接恢复等真实能力组织页面。内部工作台保持桌面优先和高信息密度，客服共享队列在领取前只展示最小摘要，领取后才展示授权详情；补偿审批队列在领取前只展示提案摘要，领取有效审批租约后才展示审批视图与决定操作。

所有数据、按钮和状态都以当前 Spring API、当前身份、页面 capability、客户归属、客服工单分配、审批租约、补偿提案版本、SSE 重授权、CSRF 与幂等契约为准。不存在真实接口或字段的原型区域直接删除并重排版式，不保留假按钮、空壳功能或模拟成功反馈。原型中没有真实契约支撑的“AI 建议”改为由真实提案依据、资格校验和权威金额组成的信息区域，不推断或伪造批准建议。

允许在必要时适当拆分 React 组件：提取稳定、可复用的视觉基础组件和状态组件；保持客户壳与内部壳分离；在客服与审批工作区内部按队列、授权详情、操作区和连接状态拆分复杂组件。组件拆分服务于可读性、测试接缝和复用，不建立跨权限投影的通用“大组件”，也不改变现有网络请求与授权责任。

## User Stories

1. 作为客户，我希望客户帮助中心使用温暖、清晰且一致的视觉设计，以便能够快速理解当前服务状态和下一步操作。
2. 作为客户，我希望客户登录页与帮助中心属于同一视觉体系，以便登录前后不会像进入两个不同产品。
3. 作为客户，我希望登录页只在本地演示环境展示后端返回的演示账号，以便演示辅助不会被写死或进入生产环境。
4. 作为客户，我希望帮助中心只要求真实接口支持的订单引用与问题描述，以便不会看到无法提交的附件、商品或联系信息字段。
5. 作为客户，我希望创建客服工单时看到明确的提交中、成功、失败和结果未知反馈，以便不会因不确定响应重复提交。
6. 作为客户，我希望进入已有客服工单时看到易理解的生命周期状态与处理模式，以便知道当前由 Agent 还是客服主导处理。
7. 作为客户，我希望调查中状态通过进度、时间线和解释性文案呈现，以便了解系统仍在工作而不是页面卡死。
8. 作为客户，我希望等待客户状态突出显示当前有效的客户澄清请求，以便能够准确补充缺失信息。
9. 作为客户，我希望提交客户澄清后看到权威恢复结果，以便不会把请求已接收误认为调查已经完成。
10. 作为客户，我希望请求转人工时看到确认、处理中和最终结果，以便不会因响应丢失多次提交相同请求。
11. 作为客户，我希望人工处理模式使用明确但不过度承诺的文案，以便知道客服已接手而不会看到仓库无法保证的响应时间。
12. 作为客户，我希望已解决和已关闭状态只提供真实允许的回复入口，以便不会看到无法执行的重新打开或继续处理按钮。
13. 作为客户，我希望公开沟通与内部事实在视觉和数据上保持隔离，以便不会接触调查事实、内部记录或审批证据。
14. 作为客户，我希望连接中断、重新同步和恢复成功都有清晰反馈，以便知道页面数据是否仍然权威。
15. 作为客户，我希望 Session 失效或主体变化后页面立即清除旧数据并返回正确登录入口，以便上一主体的信息不会残留。
16. 作为内部工作人员，我希望内部登录页使用与客户侧一致的品牌语言但明确区分内部语境，以便不会误入客户入口。
17. 作为双角色内部工作人员，我希望工作区选择页清楚呈现我有权进入的客服与审批工作区，以便登录后能够选择当前职责。
18. 作为双角色内部工作人员，我希望工作区选择页不加载任何业务队列，以便轻量入口不会扩大数据投影。
19. 作为客服，我希望共享队列采用适合桌面浏览的高密度表格与预览布局，以便快速比较真实队列条目。
20. 作为客服，我希望领取前只看到工单标识、生命周期状态、处理模式和进入时间等真实摘要，以便界面不会暗示我已获得详情权限。
21. 作为客服，我希望队列没有条目、加载失败、连接中断或正在重新同步时看到一致的状态组件，以便知道当前列表是否完整。
22. 作为客服，我希望领取工单前看到明确确认，以便理解领取会建立当前客服工单分配责任。
23. 作为客服，我希望领取成功后才加载客户标识、订单引用、问题描述、公开沟通、调查事实和业务时间线，以便界面与授权边界一致。
24. 作为客服，我希望客服工单分配被撤销时页面立即移除详情和操作，以便不会继续查看陈旧授权数据。
25. 作为客服，我希望调查事实、公开沟通和业务时间线具有清晰且不同的信息层级，以便不会把内部事实误解为客户消息。
26. 作为客服，我希望当前尚无接口支持的搜索、筛选、回复、转派、解决、导出或订单查询操作不出现在界面中，以便不会产生虚假能力预期。
27. 作为审批人，我希望审批队列使用高密度桌面布局展示提案版本、补偿方式、金额、提交时间和到期时间等真实摘要，以便快速选择待处理提案。
28. 作为审批人，我希望未领取提案时不能看到审批证据或决定按钮，以便队列可见性不会被误认为审批视图授权。
29. 作为审批人，我希望领取提案时看到明确反馈，并且只有取得当前有效审批租约后才进入审批详情，以便理解责任与授权同时建立。
30. 作为审批人，我希望审批详情将提案摘要、规则资格校验、证据引用、责任链和决定操作清晰分区，以便独立核对权威事实。
31. 作为审批人，我希望界面只展示真实提案依据，不显示接口未提供的“AI 建议批准”或虚构风险结论，以便不会把前端推断当作业务建议。
32. 作为审批人，我希望权威金额、提案金额、补偿方式和政策信息具有明确标签，以便不会混淆建议、规则结果和最终决定。
33. 作为审批人，我希望批准、驳回并转人工以及释放审批责任前出现与风险相称的确认，以便避免误操作。
34. 作为审批人，我希望驳回操作明确要求真实内部理由，以便前端不会提交不完整决定。
35. 作为审批人，我希望租约过期、释放、被替换或提案版本冲突后立即移除证据和决定按钮，以便陈旧页面不会继续暗示拥有审批权。
36. 作为审批人，我希望操作响应不确定时界面阻止普通重复提交并恢复权威状态，以便保持幂等和并发安全。
37. 作为已登录但缺少页面 capability 的人员，我希望看到清晰、非技术化且不泄露业务数据的 403 页面，以便理解当前身份不能进入该工作区。
38. 作为访问未知地址的人员，我希望看到符合统一视觉语言的 404 页面，以便返回可访问区域而不会获得资源存在性线索。
39. 作为任意使用者，我希望状态不仅依赖颜色，还同时使用文字、图标和结构，以便状态对色觉差异用户仍然可辨认。
40. 作为桌面端内部工作人员，我希望常用信息和下一步操作在正常桌面宽度下无需过度滚动即可找到，以便保持高效处理。
41. 作为维护者，我希望客户壳与内部壳继续独立，以便共享视觉基础不会造成导航或数据投影混用。
42. 作为维护者，我希望视觉基础组件和状态组件能够在多个页面复用，以便颜色、间距、标签、提示和反馈保持一致。
43. 作为维护者，我希望复杂工作区按职责适当拆分组件，以便队列、授权详情、操作区和连接状态可以独立理解和测试。
44. 作为维护者，我希望组件拆分不改变现有 API DTO、请求时序或授权判断，以便视觉重构不会成为业务重构。
45. 作为维护者，我希望工作区继续按路由延迟加载，以便视觉组件不会进入不需要的客户首屏静态闭包。
46. 作为维护者，我希望视觉改造继续通过现有严格 schema、SSE 恢复、幂等、CSRF 和权限负向测试，以便样式变化不会削弱安全保证。
47. 作为演示者，我希望客户、仅客服、仅审批人和双角色账号都能完整展示对应视觉和权限状态，以便一次演示即可证明三个投影彼此隔离。
48. 作为评审者，我希望正式页面不包含原型导航、状态画廊入口或模拟统计数据，以便能明确区分设计参考和产品实现。

## Implementation Decisions

1. 高保真 HTML 原型是视觉、布局、状态表达和交互反馈的设计基准，不是路由、API、DTO、权限或测试数据契约。
2. 正式实现采用原型的森林绿、深军绿、米白和鼠尾草绿主色，使用衬线展示字体与清晰的无衬线正文字体组合，保持克制的圆角、边框和阴影。状态通过颜色、图标和文字共同表达。
3. 客户侧采用温暖、轻量、解释性强的布局；内部工作台采用深色导航与浅色高密度内容区，并以桌面端为本轮支持目标。
4. 内部工作台不新增移动抽屉、移动导航或手机端专用布局。窄屏不得破坏数据或权限状态，但移动端完整可用性不属于验收目标。
5. 保留既有客户路由、内部路由、双角色选择页、弃用重定向和受控返回地址行为。原型中的详情路由只用于理解页面对应关系，不进入正式路由契约。
6. 保留当前身份、页面 capability 与静态工作区注册表。菜单和页面守卫继续只改善体验，不能替代 Spring 的客户归属、客服工单分配、审批租约、提案版本或禁止自审校验。
7. 客户、客服和审批页面只渲染各自真实 API 投影中的字段。原型独有字段不以占位、空值、前端猜测或静态模拟数据补齐。
8. 当真实 DTO 少于原型展示字段时，允许删除原型区域并重新分配栅格、留白和信息层级；视觉一致性不要求逐列或逐卡片复制。
9. 不存在真实 API 的按钮、筛选、搜索、分页、导出、附件、通知、转派、回复、解决、订单查询或其他操作不显示，也不通过禁用按钮或成功提示模拟存在。
10. 客户帮助中心继续使用真实的订单引用和问题描述创建客服工单，并保留当前生命周期、处理模式、公开沟通、客户澄清、转人工、回复和 SSE 恢复契约。
11. 客服共享队列继续只显示最小摘要；客服工单详情只在取得当前有效客服工单分配后请求和渲染。分配撤销、404 或 SSE 重授权失败时立即清除受保护详情。
12. 审批队列继续只显示可领取提案摘要；审批详情只在取得当前有效审批租约后请求和渲染。租约过期、释放、版本冲突或 SSE 重授权失败时立即清除证据和决定操作。
13. 审批详情不展示接口未提供的“AI 建议批准”。可以使用原型相同的视觉层级展示真实的提案理由、资格校验、权威金额、政策信息和证据，但不得生成新的业务判断。
14. 工单与提案 UUID 使用稳定的缩略形式作为主要视觉标识，并提供复制完整标识的操作。缩略形式只是展示，不成为新的业务标识或 API 输入。
15. 不虚构 `TKT-*`、`PRP-*` 等业务短号。游标、处理代次、租约令牌、内容摘要、schema 和其他纯协议字段保留在客户端协议处理中，不直接显示给用户。
16. 本地演示账号继续从后端动态取得，选择演示账号只填充真实登录表单。不得采用原型中写死的用户名、密码或身份切换方式。
17. 客户壳与内部壳继续分离；客服与审批工作区继续作为独立延迟加载区域。共享视觉资产与组件不构成代码分包或授权边界。
18. 允许提取设计令牌、品牌标识、页面标题、状态标签、连接提示、空态、错误态、骨架屏、通知、确认对话框、标识复制等稳定视觉基础组件。
19. 允许在客服工作区内按队列摘要、授权详情、调查事实、公开沟通、业务时间线和连接状态拆分组件；允许在审批工作区内按队列摘要、租约状态、提案摘要、资格校验、证据与决定操作拆分组件。
20. 组件拆分以降低复杂度、改善复用和形成外部行为测试接缝为目的。不得建立同时接受客户、客服和审批完整 DTO 的通用组件，不得把授权状态复制为与服务端事实平行的前端权威状态。
21. 优先复用当前 React Router、Ant Design 与 Pro Components 能力；没有必要时不新增 UI 框架、状态管理库、图标库或动画依赖。
22. 动画限于页面进入、状态切换、通知和确认反馈，并尊重减少动态效果的系统设置。动画不能延迟撤权后的清屏，也不能遮盖请求结果。
23. 403、404、加载、空数据、错误、断线、重新同步、权限撤销、租约失效、提交成功和结果未知都使用统一视觉语言，但文案和可用操作以各业务上下文的真实行为为准。
24. 可访问性至少包括语义化标题与表单标签、键盘可操作、明确焦点状态、对比度、非纯颜色状态表达、对话框焦点管理和减少动态效果支持。
25. 本规格不修改数据库、Spring API、Agent、补偿执行、认证模式或领域状态机；任何发现的契约缺口必须另行提出，不得在视觉实现中静默扩展后端。

## Testing Decisions

1. 最高测试接缝是现有真实浏览器全栈验收：从真实密码登录开始，经 React、Spring Security、业务服务与 PostgreSQL，从页面、HTTP 结果、SSE 投影和撤权后的可见状态验证行为。视觉重构不能用纯静态截图替代该接缝。
2. 浏览器验收覆盖未登录、客户、仅客服、仅审批人和双角色内部工作人员，证明两个界面壳、静态落点、403、404、退出、主体替换和跨标签页清理仍然成立。
3. 客户浏览器验收覆盖创建客服工单、恢复已有工单、调查中、等待客户、人工处理、已解决、已关闭、客户澄清、转人工、公开回复、断线和重新同步等当前真实状态。
4. 客服浏览器验收覆盖共享队列最小摘要、领取后详情、领取前不得预读详情、分配撤销后清除详情、断线恢复和无权资源 404。
5. 审批浏览器验收覆盖队列摘要、领取租约后才显示证据、批准、驳回并转人工、释放、租约或版本失效后的清屏、结果未知时禁止普通重试以及禁止自审隔离。
6. React 行为测试继续在现有路由、登录、客户工作区、客服工作区和审批工作区接缝上断言用户可见行为，不断言组件是否被拆成特定文件、内部 state 名称或 CSS 类名。
7. 视觉基础组件只在存在独立外部行为时增加直接测试，例如复制完整标识、确认对话框、键盘交互、减少动态效果或状态文案；纯展示组件优先通过页面行为覆盖。
8. 严格 schema 测试继续拒绝未知、缺失或类型错误的数据。实现不得为了匹配原型而放宽客户公开投影、客服工作台或审批视图 DTO。
9. SSE 测试继续覆盖 cursor 缺口、快照恢复、非法事件、Session 失效、主体替换、客服工单分配撤销和审批租约撤销；撤权后的受保护内容必须立即不可见。
10. 写操作测试继续覆盖 CSRF、幂等键、审批租约令牌与版本、提案内容摘要、驳回理由以及响应不确定后的权威查询。
11. 路由与 bundle 测试继续证明客户与内部壳分离、双角色选择页不预读业务数据、业务区域按路由延迟加载，并且内部视觉依赖不进入客户首屏静态闭包。
12. 布局验收以桌面视口为主，至少覆盖常见笔记本与桌面宽度下的客户页面、内部队列、授权详情和审批操作。内部工作台手机端完整可用性不作为通过条件。
13. 可访问性验收覆盖键盘遍历、可见焦点、表单标签、状态非纯颜色表达、确认对话框焦点管理和减少动态效果设置。
14. 视觉验收以原型的配色、字体层级、空间节奏、客户与内部布局关系及状态组件语言为比较基准；不要求复制模拟字段、静态统计数字或无真实能力的控件。
15. 完成前运行前端格式检查、Lint、类型检查、行为测试、生产构建和 bundle 证据，再运行仓库根级完整门禁。只通过 jsdom 或只通过截图都不算完成。

## Out of Scope

- 不新增或修改 Spring API、数据库 schema、领域状态、认证方式、角色、页面 capability、客户归属、客服工单分配、审批租约、提案版本、禁止自审、CSRF、幂等或 SSE 协议。
- 不新增客户工单列表、短号搜索、附件、商品详情、订单详情、物流跟踪、承诺响应时间、站内消息、邮件同步或客户资料管理。
- 不新增客服队列搜索、筛选、分页、导出、优先级、风险、SLA 统计、客户姓名、电话、VIP、回复客户、转派、解决工单、知识库或模板中心。
- 不新增审批搜索、筛选、分页、导出、批量操作、风险评级、自动审批或接口未提供的 AI 建议。
- 不实现原型的状态画廊生产路由、右下角原型导航、模拟账号、模拟数据或静态成功 Toast。
- 不创建虚构的 `TKT-*`、`PRP-*` 业务编号，也不把缩略 UUID 建模为新的业务标识。
- 不把游标、处理代次、租约令牌、内容摘要或 schema 等纯协议字段变成面向用户的产品信息。
- 不把内部工作台扩展为手机端产品，不增加移动抽屉、移动导航或移动端专用交互。
- 不整体迁移至新的前端框架、后台模板、状态管理方案或 CSS 技术栈，不为视觉效果引入未经验证的大型依赖。
- 不在本规格中正式交付实现、推送实现分支、创建实现 PR 或合并代码；后续实施需要独立干净分支和单独交付流程。

## Further Notes

- 本规格建立在既有“一个 React 应用、两个界面壳”“渐进采用内部工作台组件栈”“分离登录入口并保持单主体 Session”三个已接受架构决策之上，不替代或修改这些决策。
- `Stellogic` 品牌语言在当前前端和原型中一致，可以继续使用；原型中的人物、订单、商品、金额、时间、队列统计和演示凭据均不是验收数据。
- 原型中的客户侧“主内容＋辅助侧栏”、客服侧“队列＋授权预览”、审批侧“事实证据＋决定区”是布局方向；当真实字段不足时应收紧布局，而不是填充模拟内容。
- 组件拆分是否必要由复杂度、复用和测试接缝决定。小型纯展示区域可以保留在页面组件中，复杂状态流程不得为了追求文件数量而机械拆分。
- 本规格的测试接缝沿用仓库当前最高层真实浏览器验收、现有 React 行为测试和根级完整门禁，符合用户已确认的“视觉以原型为准，数据与权限以仓库为准”。
