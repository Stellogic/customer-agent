# #165 订单补偿额度仲裁与交付证据

关联：[Issue #165](https://github.com/Stellogic/customer-agent/issues/165)。PR 与最终验证信息在交付前补齐；尚未填写不代表通过。

## 实现与贡献边界

在已合入 #164 标准补偿与 #162 延迟自动解决的 `0a9ee031ca5c5febcd0c6fb11a660c5eee83046f` 基线上，改造订单额度核算、提案存储、审批及执行加锁接缝。React 页面、RAG、模型编排、标准补偿金额、审批租约、自审限制与执行器协议均沿用已有实现。

本次代码由 Codex 辅助实现、测试和审查；这不是用户逐行手写或独立完成全部项目的证据。用户确定任务、范围与交付约束。只支持学习项目中的模拟优惠券/部分退款，不涉及真实资金或生产客户。

## 关键决策

- 复用 PostgreSQL 事务、既有 `COMPENSATION_ALLOWANCE` advisory lock 和金额预占表，不引入 Redis、分布式锁服务或另一份可漂移账本。官方依据：[事务级 advisory lock 与一致加锁顺序](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)。
- 订单配置的 `available_compensation_amount` 继续作为原有权威额度来源；每笔资格、方式和金额仍由版本化 `DelayCompensationPolicy` 计算。#165 不自行改成“每张工单都有原订单额度”，也不修改现有政策金额。
- 权威总可补偿额度 = 订单原有权威额度 − 全部工单已消费金额；有效预占 = 全部 ACTIVE 预占；剩余 = 总额 − 有效预占。已成功执行只计入 CONSUMED，不同时扣两次。无法量化的旧 `existing_compensation` 事实继续阻止新提案；有已消费账本的订单按金额汇总。
- 待审批提案是建议，可以竞争同一额度，单独汇总但不预占。批准时才原子产生预占及执行记录。审批快照沿用总额/有效预占/剩余三项，在提交批准时重新核对；事实已变化即使仍有额度，也使旧版本失效，必须刷新提案再审。
- 每张工单至多一个有效提案，派生版本沿用参与者谱系；不再用“订单＋延迟原因唯一”阻止同订单不同工单形成提案。执行记录保留提案、决定、预占、执行幂等键的唯一约束。
- 执行 READY/PROCESSING/UNKNOWN 都保持 ACTIVE 预占；成功转 CONSUMED；确认未发生转 RELEASED。驳回、失效、过期的未批准提案不占额度；批准不可撤销的既有语义不变。
- 提案只锁本工单的有效版本与过期版本，避免持有订单锁时去等待其他工单。批准在锁提案前取得订单额度锁；执行在锁执行行前取得同一锁。未添加跨工单对话查询或对外订单账本接口。

## 验证接缝与环境

沿用已授权的客服标准提案 HTTP、审批租约/决定 HTTP、执行器/模拟供应商 HTTP，以及 Issue 明确要求的真实 PostgreSQL 额度约束接缝。新增 `agent/order_allowance_smoke.py`，由最终 `scripts/check.ps1 -Issue 165` 的 smoke 阶段执行。环境使用仓库锁、独立 Compose project/tag/端口与 4 个合成订单；不是负载或生产规模测试。

预期样本：两个工单同时提案、两个审批同时竞争 30 元额度；两个 20 元数据库预占竞争 30 元额度；响应丢失后查询与重放；确认失败释放；60 元额度内两笔 26.80 元的合法组合。既有全套验收继续检查 #164/#162、失效、租约、角色和客户投影。
