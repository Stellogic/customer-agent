# 真实验收后的收敛方案讨论

状态：用户已整体确认，并于2026-09-06调用 to-spec。正式收敛规格已发布为 [#227](https://github.com/Stellogic/customer-agent/issues/227)；本文保留讨论过程，后续以正式规格及生效修订为准。未启动产品实现或新增付费调用。

## 已确认

- 第14轮结束后，原任务完成结果、费用及自有资源清理后停止。下一步先讨论，不继续付费试跑。
- 优先让学习项目的核心场景稳定可演示、机制可解释；未覆盖规格保持未完成，不以收缩范围直接关闭原验收票。
- 对已确认的问题类型，程序读取业务规则明确要求的最小事实；模型负责诉求理解、额外调查、追问及回答。无法判明或暂不支持的情况允许明确追问或转人工。
- 审查现有五类全局必读是否必要，不把当前实现直接当业务要求，不把规则明确的必需读取扩大为完整固定调查流程。
- 第一阶段核心范围：物流延迟（无需补偿或提交补偿审批，审批执行保留人工边界）、疑似重复扣款（基于支付事实解释，不能判明时追问或转人工）、同一订单多个问题（拆票、分别处理及刷新恢复）。
- 客户追加消息后的旧回复隔离、状态一致性继续作为核心正确性要求。客户和客服两套完整知识问答质量评测暂缓到下一阶段，相关 tickets 保持未完成；不据此删除已有功能。
- 稳定性标准：正常支持场景应完成预期处理；仅事实不足、冲突或超出支持范围时，追问或转人工才是正确业务结果。网络、模型格式、内部发布错误造成的转人工计失败。
- 验证前冻结样本、次数和预算，保留所有失败；不以单次成功宣称稳定，不无限重跑追求连续成功。具体次数和预算待调用规模查明后确定，当前没有新增付费授权。
- 先独立交付已定位的确认、回复发布及审计归属等修复，再调整调查流程。各阶段有自身回归和完整门禁，不等待 #174 全部通过才交付产品修复；#174 保持原验收要求，未满足则不关闭。
- 第二阶段允许定向整理物流延迟与重复扣款涉及的调查、结论和回复字段契约：物流延迟使用物流事实，重复扣款使用支付事实，消除后者对延迟字段的非业务必要依赖；公共订单、政策和补偿待办校验保留，模型可追加调查。不搭建通用工作流平台，不重写全部模块。
- 对业务规则已明确的必需证据对应关系，程序根据实际取得的权威事实构造记录，模型不再重复填写这些机械对应关系。模型负责是否补查、补充证据选择和事实如何回答客户问题；Spring 继续校验来源、时效、冲突和资格。缺失事实仍失败，不补造证据，不将支付记录等同于已证实重复扣款。该决定须与必需读取边界一起更新正式 ADR 和规格，不能伪称现有自治契约未改变。
- 重复扣款第一阶段成功终点：说明已知支付事实，明确不能确认的部分，保留上下文交人工核查。暂不新增逐笔交易对账能力，不声称查明扣款原因或完成退款。该预期业务转人工与技术故障转人工分别判定。

## 核对所得的约束

目标运行工作树为 Issue #174 的独立验收 worktree。其已接受 ADR `docs/adr/0006-bounded-level-two-agent-autonomy.md` 和 `docs/specs/issue-149.md` 要求模型自主决定调查路径及证据组合，Spring 保持业务权威；两份文件没有明确要求每次工具执行前分别调用一次模型。实现前需要明确记录必需事实读取与剩余自主调查的边界，并同步受影响规格。

当前 `_allowed_actions` 要求补齐五类事实才允许提交结论，是代码约束；尚未证明每类问题都业务必需。自动化这些动作与按问题裁剪事实集合是两个不同决定。

本地 D:/customer-agent 存在用户未提交的 CONTEXT.md 修改和未跟踪的旧自治 ADR，本讨论不覆盖它们，也不依据旧文件编号新建正式 ADR。整体方案达成共识后，再在正确基线落正式决定。

## 新增事实核对

- 第14轮已结束，原任务状态为 idle。本轮仍 INCOMPLETE：重复扣款结论再次被 Spring 以 INVALID_EVIDENCE_APPLICABILITY 拒绝，未记录具体缺项；本轮无回复流失败。结果见目标工作树 `docs/delivery/issue-174-live-14-result.md`。

- 但当前调查结论校验、Agent 判断与回复输入仍有全局延迟字段依赖。因此按问题裁剪读取需要检查端到端字段契约，不能只删除 `_allowed_actions` 的必读项。用户已接受在第二阶段定向整理该耦合，具体字段方案待核对。

## 已确认的分阶段执行方案

### 1. 固定基线并交付已定位修复

回读最新主线、PR #214/#226 的实际改动及第14轮交接，不覆盖共享或脏工作树。将已定位的确认命令、审计归属、流片段与发布纠正修复整理为可独立验证的产品切片；已有提示调整和验收文档逐项归属，不把整个混合分支无差别当作已验证修复。优先复用已有回归，缺失时补覆盖实际故障路径的回归。审查及完整门禁通过后按切片自身要求交付，不能因此宣称 #174 通过。

### 2. 落正式职责决定并定向重构

在正确主线基线上新增 ADR，部分替代0006中必需读取和机械证据组合的归属，同步正式规格及镜像，保留历史。以 Spring 场景规则为权威核对必需事实，不再维护彼此独立的必需证据清单；具体复用方式采用最小改动，不新建规则平台。

程序执行明确必需读取，并从真实、授权、当前代次事实构造必需证据关系。模型可在现有授权能力与预算内追加调查、检索、追问和形成有依据回复；语义判断不能用机械证据映射替代。原有人工审批、状态、资格、金额及副作用权威保留。

同步整理 Agent 的事实归一化、判断、沟通及结论输入，和 Spring 的结论解析、场景校验及回复事实校验。重复扣款不再依赖无业务必要的物流字段；物流延迟不因裁剪丢失补偿资格证据。澄清恢复路径以及确定性测试模型使用同一场景契约。现行政策在支付场景的业务适用性需核对，不因代码要求就声称必需。

### 3. 建立能定位失败的验证反馈

在新增真实调用前，为错误保存稳定分支码、缺失事实或适用性类别、能力与调用归属；不保存原始prompt、响应、思维链或密钥。复用模型审计接缝核对usage缺失，未知费用仍保留未知。

先离线验证每个修复或契约，再做失败场景的有界真实诊断，最后运行冻结的核心端到端验证。诊断不冒充发布验收；预算或全局故障触发停止时仍停止，不用场景拆分绕过限制。每次变更只为验证明确假设，不原样无限整轮重跑。

核心验证覆盖：物流无补偿与待审批两种结果；重复扣款有依据回复后交人工；同订单拆票及恢复；追加消息旧代次隔离；技术故障明确失败且不产生错误成功结果。验收证明重复扣款无需物流/订单规则、物流延迟无需订单规则即可完成相应路径，同时必需证据缺失仍被拒绝。

付费验证前依据完成后的实际调用路径提出具体样本、次数、token/费用上限和业务副作用，另获执行授权。保存全部结果，报告范围内重复验证表现，不外推生产稳定性。#174和完整知识问答评测仍按各自原要求管理，核心演示通过不直接关闭它们。
