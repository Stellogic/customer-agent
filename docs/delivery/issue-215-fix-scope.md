# #215 最小修复约定

2026-09-04 经用户确认。本文是本票的轻量实施记录，沿用现有领域定义和 ADR 0007，不新增正式规格层级。

## 问题与目标

真实诊断观察到首次受理漏掉问题，以及客户明确回答后澄清流程不推进。历史“错误进入受理协助”的根因仍未确认，不能将这几种现象直接视为同一原因。证据见[诊断记录](issue-215-intake-diagnosis.md)。

目标是让客户用自然语言描述同一订单“包裹没收到、疑似重复扣款”，完成必要澄清后统一确认，成功创建两张工单。

## 最小实现方向

- 分别检查首次问题识别和后续澄清推进，依据证据做局部修复，不限定只能修改提示词。
- 允许模型理解当前回答、程序保留已有问题并执行明确的状态更新；具体接口在核对现有实现后确定，不预设重构。
- 含糊回答仍需澄清。澄清问题不等于确认建单，也不等于核实客户陈述的业务事实。
- 保持客户统一确认后由 Spring 原子创建工单、各工单引用同一共同受理记录的现有规则。

## 验收

优先复用现有浏览器入口，验证 React → Spring → LangGraph → 真实模型的完整行为：

1. 上述输入中的两个问题均被保留，可以直接进入拟建工单集，也可以先待澄清；不强制固定提问次数。
2. 对实际提出的问题给出明确回答后，流程正确推进，已有问题和其他待澄清问题不丢失，不错误进入受理协助。
3. 客户看到完整的两项拟建工单并统一确认；确认前没有正式工单，确认后原子创建两张工单，共享共同受理记录。

为实际修复补充直接相关的回归，复用现有测试入口，检查外部行为。真实路径通过后不追加多轮稳定性证明；正式交付仍执行仓库规定的检查与审查、合入和关票流程。

## 边界与未决事项

不扩展罕见场景、不重构整个受理流程，也不以放宽校验或伪造模型结果取得通过。首次遗漏与澄清不推进是否同源仍待查证；历史错误转人工若未复现，保留“原因未确认”的结论。

本约定确认修复目标与允许的范围，不代表修复已经完成。真实调用继续遵守已有外发授权和累计费用边界。
