# Agent 嵌套知识检索并发修复

调查图会调用 Spring 的知识检索，Spring 再请求同一 Agent 服务的知识编码图。当前锁定依赖的 `langgraph_api/cli.py` 将未传入的 `n_jobs_per_worker` 转为1，虽然 CLI 帮助写的是默认10。单任务槽被父调查占用后，编码图必须等待父调查结束，形成自等待。

Compose 显式传入 `--n-jobs-per-worker 10`，沿用现有服务与接缝。原5秒工具请求期限、模型、业务校验和费用上限不变。

## 无供应商调用的红绿证据

在52daf02基线上，隔离栈通过真实受理建立工单，确定性行动模型仅用于选中知识检索；Spring、PostgreSQL、LangGraph与本地编码器均实际运行。

- 原配置：连续三次内部读取分别在5002、5005、5005毫秒超时，检查点为 `knowledge_failure=RETRIEVAL_UNAVAILABLE`，工单以 `TOOL_RETRY_EXHAUSTED` 转人工。
- 仅延长诊断期限到15秒：三次仍全部超时；父调查退出后，排队的编码才启动，每次约30毫秒。独立检索约1秒，索引为READY。
- 原5秒期限加显式10个任务槽：内部检索HTTP200，耗时863毫秒，响应字段完整，检查点不再记录知识检索失败。

上述为内部检索可返回的证据，供应商调用数为0。诊断使用的固定回复模型没有知识回答能力，后续回复校验仍失败；这不构成真实模型发布验收通过。临时诊断副本与原始日志均未纳入产品代码。正式五场景验收仍由 #174 执行。
