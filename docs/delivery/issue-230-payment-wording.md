# 支付回复措辞误拒与事实校验修复

> 本文保留诊断与初步修复历史。后续用户确认[ADR 0011](../adr/0011-structured-authority-and-free-reply-text.md)，取消自由正文语义拦截；下述有限同义词修复已被替代，不是当前实施要求。

用户要求先重新核对代码问题，允许适度放宽模型措辞审查，但保留事实性错误校验，并以尽快可用为目标，不要求每次调查都自动完成。跨供应商对照不再是继续工作的前提；仍记录真实失败，安全转人工不冒充自动调查成功。

## 确认的代码问题

Agent 与 Spring 均要求精确的支付回复子串，导致冒号格式、“人工核实”“未进行退款”“尚不能确认”等不改变业务含义的表达被拒。同时，无条件扫描“两笔”会把“无法确认是否存在两笔扣款”误判为确认逐笔交易。相反，原扫描又漏过“已全额退款”这一未经授权的断言。

离线回归先复现：Agent新增六项等义表达均失败；Spring支付安全策略11项测试中2项失败，分别暴露等义误拒和全额退款漏检。这证明存在代码问题，不能把真实验收失败全部归因模型。旧真实失败没有保存被拒正文，不能推断每次都由上述具体措辞触发。

## 最小修复与保留边界

- 支付和全额退款状态允许“为”及中英文冒号；保留明确的聚合状态标签，要求每个匹配都与当前工单的权威事实一致，禁止同文出现相反状态。
- 允许上述有限等义表达；只略过明确表示无法确认的重复扣款／两笔扣款片段，随后继续检查其余断言。
- 保留订单范围、证据范围、金额、退款执行、审批权限、敏感信息和事实来源检查；补充全额／全部退款断言检查。不新增模型判断器，不把模型输出自动改成固定业务答案。

动作适配器仍要求单个合法JSON、枚举动作和授权证据。现有真实INVALID_JSON／SCHEMA_MISMATCH没有具体被拒内容，不能判断是格式包裹还是实质无效动作；本次不靠猜测放宽动作或证据权限。主动转人工路径仍保留，后续记录其原因和客户可接续性。
