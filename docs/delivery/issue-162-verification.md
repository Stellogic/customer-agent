# #162 五分钟延迟自动解决

## 范围与依据

本票只替换 Agent 无补偿结论的即时解决路径，不改变人工手动解决和补偿执行权限。
规格来源为 GitHub #162 和 `docs/specs/issue-149.md` 第 38–45 条。

复用仓库已有 `@Scheduled`、PostgreSQL 持久化和 `TicketAuthorityLock`，不引入任务队列依赖。
Spring 的[调度说明](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)
提供周期扫描机制，但进程内调度本身不保存业务期限；期限保存在数据库。
PostgreSQL [显式锁](https://www.postgresql.org/docs/17/explicit-locking.html)
用于串行化客户消息和到期决策。该组合沿用现有七十二小时关闭调度；五分钟是本项目规格，不是外部默认值。

## 业务边界

- `auto-resolution-v1` 是 Spring 白名单：权威状态解释、纯规则说明、已完成的非补偿性核对。
  白名单同时核对结论理由与风险场景，不因问题类型或模型评分单独授权。
  首版将无异常的零延迟物流核对归入已完成核对；退款/重复扣款仍转人工。
  所有允许分支都要求全部客户原文符合版本化的明确查询问句；无法明确区分的操作诉求转人工。
  已经由 Spring 校验并持久化的订单澄清确认码不作为新的业务诉求，但普通续回复仍重新检查。
- 完整公开回复与候选在同一事务持久化。候选关联回复 ID、结论证据、Agent 代次和最新客户消息序号；
  期限固定为持久化回复后五分钟，刷新、重登和重启不重置。
- 调度取得工单权威锁后重读最新工单、代次、客户消息版本、完整回复、证据来源/时效/冲突、
  最新订单事实、待办、补偿和人工偏好。已接受新消息先取消候选；先完成解决的并发消息须按既有重开路径处理。
- 订单事实、待办和补偿写入共享既有订单额度锁，避免到期读取与事实变更穿插。
  未通过重校验时停止自动解决并展示重新评估；客户可继续回复触发新调查。
- 客户取消联合当前候选截止时间与公开 Agent 代次仲裁，旧页面不能取消新候选。取消重试不重设期限。
- v2 客户快照/SSE 只公开状态和截止时间；v1 快照字段不变。前端归零只等待 Spring 结果，绝不自行变为已解决。
- 解决后继续使用既有 `TicketResolutionTransition` 的七十二小时关闭期限与重开语义。
