# #230 显式订单受理范围修复

## 问题与最小修复

客户明确输入一个订单号时，正式受理适配器仍向模型提供所有可见订单。供应商可以返回结构合法但语义过宽的待处理订单队列；后端确认当前订单后因此进入不应发生的下一订单识别。下一订单校验失败会使同一确认事务回滚。可见订单属于权限范围，不等于客户要求处理的范围。

现在复用既有订单号匹配逻辑：开始受理且客户明确提及可见订单号时，仅把这些订单作为模型输入、schema枚举及响应校验范围；匹配保留文本顺序、大小写不敏感及同位置最长订单号优先。没有明确订单号时继续保留全部可见候选，供模型按自然语言线索识别。已有订单上的澄清和修改不收窄，以保留当前状态合同。

受理输入版本更新为intake-v4。Spring事务、队首校验及确认规则不变，没有新增依赖。

## 离线证据

order-scope-red01以30个可见订单和只提及一张订单的输入复现29个多余队列项；两张明确订单的输入也错误夹入其余订单。供应商使用HTTP替身，不请求外部服务。修正后两个用例通过，新增无显式编号的自然语言候选保留用例。全量Agent回归551 passed / 3 skipped，格式、lint及类型检查通过。

核心供应商夹具现在故意将输入中的其余候选全部排队，避免仅验证供应商恰好遵循提示。浏览器矩阵对单订单物流场景增加独立审计断言：成功确认后仅有一次受理模型调用，不应进入NEXT_ORDER。order-scope02的五类共10项加强矩阵通过，52次受控调用全部归属、未知usage及未结算均为0，资源清理读回通过。该矩阵测试的是提交前工作树；最终提交需通过完整门禁，结果以修复PR记录为准。前一轮scope01因新增断言格式停止，业务未执行；格式修正后重新运行，不将前一轮计为通过。

## 结论边界

这项修复处理已离线复现的订单范围缺口。真实失败响应没有保留模型答案正文，因此不宣称唯一还原了具体拒绝分支。离线通过也不能替代冻结真实核心场景，#230继续保持OPEN，#174及完整知识质量评测继续暂停；不自动追加付费验证。
